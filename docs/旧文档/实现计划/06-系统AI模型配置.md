# 06. 系统级 AI 模型配置（独立表 + 独立页面）

## 目标

让管理员为**系统侧**（worker 任务、后台分析、自动摘要等）配置 AI 提供方（OpenAI / Anthropic / DeepSeek / 通义 / 月之暗面 / 智谱 等），与**用户私人 AI Keys**（`user_ai_keys` 表）完全隔离。

关键点：

- 敏感字段（API key / token）用与数据源相同的 **Argon2id+AES-GCM** 加密落库
- 管理端有独立页面 `/system-ai`，与数据源页区分
- 系统服务（analyzer、ai service 等）通过 `GetActive()` 拿到**当前启用**的 provider 及 key

## 背景

- 项目已有 `user_ai_keys` 表（用户自带 key）和 `ai_service`（调用入口）
- 尚无"系统持有"的 AI 配置位——当前用 ENV `OPENAI_API_KEY` 等硬注入，不便管理
- 要求：改完立刻生效（热加载，同 01 号文档思路）

## 设计决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 表设计 | 新建 `system_ai_configs`，与 `data_source_configs` 解耦 | 字段差异大（model list / temperature / timeout / 组织 ID 等） |
| 加密 | 复用 `SecretBox`（同 master key） | 运维同一套密钥管理 |
| "启用"语义 | 同一时刻允许多个 provider 被启用，但 **每个 "用途"（purpose） 只选一个 primary** | 允许主备切换 |
| purpose 维度 | `chat` / `embedding` / `summarizer` / `reasoning`（预设枚举） | 不同任务可用不同 provider |
| 模型列表 | `models TEXT[]`，服务调用时指定具体 model | 一个 provider 往往支持多个 model |
| 热加载 | Redis Pub/Sub channel `system_ai:changed`，与 01 文档相同模式 | 统一 |
| 与用户 AI key 隔离 | 绝不 mix；service 接口明确参数 `scope=system \| user` | 避免泄露 |

## 数据模型

### 新表

```sql
CREATE TABLE IF NOT EXISTS system_ai_configs (
    provider_id        TEXT PRIMARY KEY,            -- openai / anthropic / deepseek / qwen / moonshot / zhipu / azure_openai / 自定义
    name               TEXT NOT NULL,               -- "OpenAI 官方" / "DeepSeek V3" / ...
    base_url           TEXT NOT NULL DEFAULT '',    -- 自定义网关时用；空则用 provider SDK 默认
    organization       TEXT NOT NULL DEFAULT '',    -- OpenAI org id 等
    models             TEXT[] NOT NULL DEFAULT '{}', -- ["gpt-4o","gpt-4o-mini"]
    default_model      TEXT NOT NULL DEFAULT '',
    temperature        DOUBLE PRECISION NOT NULL DEFAULT 0.2,
    timeout_seconds    INTEGER NOT NULL DEFAULT 60,
    max_tokens         INTEGER NOT NULL DEFAULT 4096,
    purposes           TEXT[] NOT NULL DEFAULT '{}', -- ["chat","reasoning"]
    primary_for        TEXT[] NOT NULL DEFAULT '{}', -- ["chat"] 表示作为 chat 的 primary

    secret_ciphertext  BYTEA,
    secret_salt        BYTEA,
    secret_nonce       BYTEA,
    has_secret         BOOLEAN NOT NULL DEFAULT FALSE,

    enabled            BOOLEAN NOT NULL DEFAULT FALSE,
    created_at         TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_by         TEXT NOT NULL DEFAULT ''
);

CREATE INDEX IF NOT EXISTS idx_system_ai_enabled ON system_ai_configs(enabled);
```

### `/test` 接口

- 对 primary provider 发一次 `ping` 级调用（如 OpenAI 的 `models.list` 或 1 token chat）
- 响应：
  ```json
  { "ok": true, "latency_ms": 420 }
  { "ok": false, "error": "401 invalid api key", "latency_ms": 95 }
  ```
- 不写入任何结果；仅供管理端验证

## 关键流程

### Service 层

```go
// internal/service/systemai/service.go
type Config struct {
    ProviderID, Name, BaseURL, Organization, DefaultModel string
    Models, Purposes, PrimaryFor []string
    Temperature float64
    TimeoutSeconds, MaxTokens int
    HasSecret, Enabled bool
    UpdatedAt time.Time
    UpdatedBy string
}

type Service struct {
    pool   *pgxpool.Pool
    box    *crypto.SecretBox
    audit  *audit.AuditService
    rdb    *redis.Client
}

// 只读：List / Get
// 写：Update / Enable / Disable（内部发 Redis Pub/Sub）
// 业务专用：GetActive(ctx, purpose) (Config, string /*secret*/, error)
//          Test(ctx, providerID) (TestResult, error)
```

`GetActive` 查询逻辑：

```sql
SELECT * FROM system_ai_configs
WHERE enabled = TRUE AND $1 = ANY(primary_for)
ORDER BY updated_at DESC LIMIT 1
```

若无命中，降级查 `$1 = ANY(purposes)`；再无则返回 `ErrNoActiveProvider`。

### Handler

参考 `@/home/mluser/code/antclaw/backend/internal/adapter/rpc/datasource_handler.go` 的结构实现 `system_ai_handler.go`：

- `PubKey` 复用（不要重复注册路由）
- `List` / `Get` / `Update` / `Enable` / `Disable` / `Test`
- 所有写接口走 `VerifyRequestSignature`；带敏感字段的走 hybrid envelope
- 写成功后：
  1. 写审计（`ai.<action>`）
  2. `rdb.Publish("system_ai:changed", {"provider_id":...})`

### 热加载（worker / analyzer）

`internal/service/ai`（已有调用入口）增加 `*systemai.Service` 依赖，改为：

```go
cfg, secret, err := systemAISvc.GetActive(ctx, "chat")
if err != nil { return err }

client := openai.NewClient(secret, openai.WithBaseURL(cfg.BaseURL))
```

- 不再从 ENV 读 key
- ENV `OPENAI_API_KEY` 等仅作启动预置（首次通过 CLI 一键导入到 `system_ai_configs`）

订阅 `system_ai:changed` 后清空本地缓存，下一次 `GetActive` 会读到新值。

## 注意事项

- **严禁与 `user_ai_keys` 混用**：service 接口必须显式区分 scope；代码审查时重点关注
- **清除密钥后的调用**：业务层 `GetActive` 必须在 `has_secret=false` 时显式返回 `ErrNoSecret`，让上层优雅降级而非空 key 去调 API
- **`/test` 严格限流**：Redis `RATE:ai-test:<provider_id>` → 每 10 秒最多 1 次；避免刷 key
- **models[] 字段校验**：长度 ≤ 50；每项长度 ≤ 100；禁止特殊字符
- **purposes / primary_for 约束**：`primary_for ⊆ purposes`；service 层校验，不依赖 DB CHECK（灵活）
- **兼容 Azure OpenAI**：`base_url` 可指向 Azure endpoint；`organization` 复用存 deployment name（前端 label 随 provider 切换）
- **日志脱敏**：error 消息若包含上游 API 返回的 key echo，**必须过滤**；Test 失败时只展示 error code

## 风险与回退

- 风险：运维误删 primary provider → `GetActive` 失败 → AI 相关任务失败
  - 缓解：前端禁用 primary 的 provider 时给警告；service 层 `Disable` 若会导致某 purpose 无 primary，默认返回 409 + 强制参数 `?force=true`
- 风险：ENV 与 DB 两处都有 key → 歧义
  - 缓解：启动日志明确打印来源；新部署优先使用 DB
- 回退：把业务代码 fallback 到 ENV；前端页面禁用；`system_ai_configs` 表不删
