# 01. 配置热加载：API → Worker（Redis Pub/Sub）

## 目标

管理员在管理端修改某个数据源（api key / endpoint / 清除密钥）后，**Worker 无需重启即可生效**。

## 背景（当前状态）

- Worker 启动时调用 `resolveFredKey(ctx, pool, logger)` 一次性解析；
- 变更后必须 `docker compose restart worker` 才能生效；
- 已有 `SecretBox` + `datasource.Service.GetSecret(ctx, sourceID)` 能动态解密。

## 设计决策

**事件驱动**，不要轮询。Redis 已在项目中使用（SSE / nonce 防重放），继续复用。

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 通知通道 | Redis Pub/Sub `channel=datasource:changed` | Worker 已持有 `*redis.Client`；pub/sub 开销低 |
| 消息体 | `{"source_id":"fred","at":169...}` JSON | 不传值，仅触发重读 |
| Worker 侧 | 一个 goroutine 订阅 → 收到消息后调 `Resolver.Reload(sourceID)` | 与业务 tick 解耦 |
| 客户端层 | 引入 `CredentialResolver` 抽象，持有 `map[source_id]string` + RWMutex | 各 collector 只读一个函数 |
| 启动时行为 | 依旧按 DB→ENV→默认 预热一次 | 避免首次运行缺 key |
| 失联期 | Pub/Sub 断连时自动重连；Worker 不阻塞业务 | 容错第一 |

无新表。

## 接口契约

### 新增内部类型

```go
// internal/service/datasource/resolver.go
package datasource

type CredentialResolver struct { /* 见"关键流程" */ }

// 构造：启动时调用，传入 pool / secretBox / env fallback map
func NewCredentialResolver(pool *pgxpool.Pool, box *crypto.SecretBox, envFallback map[string]string, logger *slog.Logger) *CredentialResolver

// 读取：任何 collector 调用；永不返回 error（失败时返回 fallback / 空串 + 内部 warn 日志）
func (r *CredentialResolver) GetSecret(sourceID string) string
func (r *CredentialResolver) GetEndpoint(sourceID string) string

// 预热 / 重载：订阅消息 / 启动时触发
func (r *CredentialResolver) Reload(ctx context.Context, sourceID string) error
func (r *CredentialResolver) ReloadAll(ctx context.Context) error

// 启动订阅：返回 stop func；内部自行重连
func (r *CredentialResolver) StartSubscriber(ctx context.Context, rdb *redis.Client) (stop func())
```

### 新增 Redis channel

- **channel**：`datasource:changed`
- **publisher**：`api` 在 `datasource_handler.go` 的 `Update` 写入成功后
- **subscriber**：`worker` 启动时订阅

### Publisher 伪代码（api 端）

```go
// 写 DB + 审计 成功之后追加：
payload, _ := json.Marshal(map[string]any{
    "source_id": sourceID,
    "at":        time.Now().Unix(),
})
_ = rdb.Publish(r.Context(), "datasource:changed", payload).Err()
```

### Subscriber 伪代码（worker 端）

```go
func (r *CredentialResolver) StartSubscriber(ctx context.Context, rdb *redis.Client) (stop func()) {
    ps := rdb.Raw().Subscribe(ctx, "datasource:changed")
    go func() {
        for msg := range ps.Channel() {
            var evt struct{ SourceID string `json:"source_id"` }
            if json.Unmarshal([]byte(msg.Payload), &evt) == nil && evt.SourceID != "" {
                if err := r.Reload(ctx, evt.SourceID); err != nil {
                    r.logger.Warn("reload failed", "source", evt.SourceID, "error", err)
                }
            }
        }
    }()
    return func() { _ = ps.Close() }
}
```

## 关键流程

### Worker 启动

```
main() 内：
1. pool, rdb, box 就绪后
2. resolver := datasource.NewCredentialResolver(pool, box, envFallback, logger)
3. if err := resolver.ReloadAll(ctx); err != nil { logger.Warn(...) }   // 预热
4. stop := resolver.StartSubscriber(ctx, rdb); defer stop()
5. fredKey := resolver.GetSecret("fred")
   if fredKey == "" { fredKey = envFallback["fred"] }  // 二次兜底
   fredClient := apiclient.NewFredClient(fredKey)      // 首次构造
```

> **重要**：由于 `apiclient.FredClient` 当前内部保存 key，热加载要生效需要让 client 也能动态取 key。
> 两种方案：
> - **(推荐)** 给 client 增加 `SetKey(string)` 方法，Reload 成功后 resolver 调用；
> - 或让 collector 每次调用前 `client = apiclient.NewFredClient(resolver.GetSecret("fred"))`（GC 友好，但每次构造开销）。
>
> 选"推荐"，更干净。`macroSvc` 同理加 `SetFredKey(string)`。

### Reload 单个数据源

```
Reload(ctx, sourceID):
  plaintext, err := svc.GetSecret(ctx, sourceID)
  if err != nil and err != ErrNotFound: return err
  r.mu.Lock()
  r.secrets[sourceID] = plaintext         // 空串也写入，代表"未配置"
  // endpoint 同理：svc.Get(ctx, sourceID).Endpoint
  r.endpoints[sourceID] = cfg.Endpoint
  r.mu.Unlock()
  // 触发注册表回调（见 02 文档）
  for _, cb := range r.callbacks[sourceID] {
      cb(sourceID, plaintext, cfg.Endpoint)
  }
```

### ReloadAll

遍历 `data_source_configs` 所有行，逐个 `Reload`。仅启动时用。

### Pub/Sub 断连恢复

`go-redis` 的 `Subscribe().Channel()` 内部有自动重连。不要手动 reconnect；只需捕获 `PubSub.Receive` 的 error 并记 warn。

## 验证步骤

```bash
# 1. 启动后修改 key
docker compose -f deploy/docker-compose.yaml up -d api worker

# 2. Worker 原始日志：收到的是 DB 中当前 key
docker logs antclaw-worker 2>&1 | grep "FRED key resolved"

# 3. 通过 /tmp/test_secure_put.py 把 FRED key 改成一个错误值
SECRET=bogus-key python3 /tmp/test_secure_put.py

# 4. 立刻观察 worker 日志（不重启）：应出现 "reload for source=fred" 或类似
docker logs --since 10s antclaw-worker 2>&1 | grep -iE "reload|fred"

# 5. 等到下一个 macro tick（1h）或手动触发 → FRED 返回 400
#    说明新 key 已生效（而不是旧 key）

# 6. 把 key 改回正确值 → 下一次 tick 恢复正常
```

## 注意事项

- **并发**：`CredentialResolver` 内部 `sync.RWMutex`，Reload 拿写锁、GetSecret 拿读锁；GetSecret 是热路径，必须轻量
- **失效不升级为 fatal**：订阅失败 / Reload 失败 → 记日志继续用旧值，不退出
- **Publisher 顺序**：先 DB commit + audit，再 publish；publish 失败不回滚
- **审计**：不要把 subscriber reload 动作当业务动作写审计；只有管理员的 PUT 写审计
- **启动竞态**：worker 启动可能早于 api；`StartSubscriber` 内 `Subscribe` 本身不依赖 api，只依赖 redis，安全

## 风险与回退

- 风险：`SetKey` 方法引入 mutable state，可能误用 → 文档注释 "仅 CredentialResolver 回调使用"
- 回退：订阅失败时 worker 行为完全等于旧实现（启动时读一次），不影响采集
