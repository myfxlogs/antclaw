# 通知推送系统

> 主动推送给客户端的统一中枢。参考 `Emulator/ark-intelligent` 的 Telegram 推送模型，
> 在 antclaw 上落地为 **持久化 + 实时 SSE + 用户偏好 + 去重** 的完整闭环。

## 1. 设计模型

```
┌────────────┐                    ┌────────────────────┐
│   业务侧    │                    │     浏览器客户端    │
│ (worker /  │                    │   (admin / web)    │
│  api 处理) │                    │                    │
└─────┬──────┘                    └────────┬───────────┘
      │ Send(Notification)                 │ EventSource('/sse/notifications')
      ▼                                    ▼
 ┌────────────────┐                 ┌──────────────────┐
 │ notify.Service │                 │  SSE Handler     │
 │  ─ Dedup       │                 │  ─ JWT 鉴权      │
 │  ─ Prefs 过滤  │                 │  ─ Pub/Sub 订阅  │
 │  ─ 持久化      │                 └────────┬─────────┘
 │  ─ Publish     │                          │
 └─────┬──────────┘                          │
       │                                     │
       ▼ Pub/Sub: user:{userID}:notifications
┌──────────────────────────┐
│         Redis            │
└──────────────────────────┘
       │
       ▼ INSERT
┌──────────────────────────┐
│   PostgreSQL             │
│   ─ notifications        │
│   ─ user_notification_   │
│      prefs               │
└──────────────────────────┘
```

### 关键约束

- **持久化与实时投递解耦**：`notify.Service.Send` 始终落库；推送链路由偏好 / 静默时段决定是否进入 Pub/Sub。即使用户离线、SSE 断开，重新打开后通过 `ListUnread` 仍能看到所有遗漏的通知。
- **去重在调用方语义层完成**：`Notification.DedupKey + DedupTTL`，由 Redis SETNX 实现；命中即静默丢弃。
- **静默时段 critical 穿透**：`severity == "critical"` 的通知绕过静默期与最低等级阈值。
- **Pub/Sub 而非 Stream**：每用户一个 channel，无消费组，断线不补发；历史靠 `ListUnread` 拉取一次即可，避免双源。

## 2. 数据模型（迁移 026）

`notifications`（在 022 的基础上扩展）：

| 字段        | 用途                                                     |
| ----------- | -------------------------------------------------------- |
| `category`  | 业务分类：`alert / signal / system / digest`             |
| `severity`  | 严重度：`low / normal / high / critical`                 |
| `dedup_key` | 调用方提供的去重键，仅作存档与查询索引                   |

`user_notification_prefs`（每用户单行）：

| 字段           | 默认                                          |
| -------------- | --------------------------------------------- |
| `enabled_types`| `{alert,signal,system,digest}`                |
| `min_severity` | `low`                                         |
| `quiet_start`  | `00:00` （`start == end` → 不静默）          |
| `quiet_end`    | `00:00`                                       |
| `timezone`     | `UTC`（IANA tz）                              |
| `push_enabled` | `true`                                        |
| `email_enabled`| `false` （预留）                              |

### `notify.Notification` 字段语义

```go
type Notification struct {
    UserID   uuid.UUID
    Type     string         // 默认 in_app
    Category string         // 默认 system
    Title    string
    Body     string
    Data     map[string]string
    Severity string         // 默认 normal
    DedupKey string         // 选填
    DedupTTL time.Duration  // 选填，默认 10m
}
```

## 4. RPC（`NotificationService`）

| 方法              | 说明                                  |
| ----------------- | ------------------------------------- |
| `ListUnread`      | 当前用户未读列表（默认 100）          |
| `ListHistory`     | 当前用户历史列表（默认 50）           |
| `UnreadCount`     | 未读数（用于铃铛 badge）              |
| `MarkRead`        | 单条标记已读，按 `(id, user_id)` 校验 |
| `MarkAllRead`     | 全部标记已读                          |
| `GetPrefs`        | 当前用户偏好；不存在则返回内置默认    |
| `UpdatePrefs`     | 写偏好；校验 `HH:MM` 与 IANA tz       |

服务挂载于 `main.go`，**默认开启 `auth.AuthInterceptor(true)`**：未登录调用直接 `CodeUnauthenticated`。

## 5. 实时通道：`/sse/notifications`

- **鉴权**：依次尝试 `Authorization: Bearer`、Cookie `antclaw_at`、查询参数 `?access_token=`（EventSource 无法定制请求头，浏览器侧使用查询参数）。
- **频道**：`user:{userID}:notifications`（Redis Pub/Sub）。
- **协议**：每条消息以 `event: notification\ndata: <json>\n\n` 推送；每 15s 一条 `: ping`。
- **断线**：浏览器自动重连；不补发历史，需要时调用 `ListUnread`。

## 7. 业务侧调用约定

最简调用：

```go
notifySvc.Send(ctx, &notify.Notification{
    UserID:   uid,
    Category: "alert",
    Severity: "high",
    Title:    "策略告警触发",
    Body:     "EURUSD 已触发回归阈值",
    DedupKey: fmt.Sprintf("alert:%d:%s", id, time.Now().Format("20060102T1504")),
    DedupTTL: 5 * time.Minute,
})
```

后续接入新业务（regime 切换、宏观异动、回测完成等）时统一走 `notify.Service`，避免重复实现 Pub/Sub / 落库 / 去重。

## 8. 验证

1. 后端 / Worker 重启后 `\d notifications` 应包含 `category / severity / dedup_key`，`\dt user_notification_prefs` 存在。
2. 直接 `INSERT INTO notifications(...)` 一条记录，前端铃铛刷新可见未读 +1。
3. `redis-cli PUBLISH user:{uid}:notifications '{...}'` 可触发已登录浏览器的实时推送（无需登录态时 SSE 端点返回 401）。
4. 设置页关闭 push_enabled / 调高 min_severity，再发同等级别消息：仅落库不实时；critical 永远穿透。

## 9. 与 ark-intelligent 推送模型的对照

| 维度        | ark-intelligent               | antclaw 实现                                  |
| ----------- | ----------------------------- | --------------------------------------------- |
| 传输        | Telegram Bot HTTP             | 浏览器 SSE（Redis Pub/Sub fanout）            |
| 收件人台账  | `ports.PrefsRepository`       | `user_notification_prefs` 表                  |
| 触发        | `Scheduler` + `time.Ticker`   | worker 现有调度循环 + RPC 写入路径            |
| 偏好/分级   | tier-based currency/impact    | `enabled_types / min_severity / 静默时段`     |
| 去重        | 内存 `sentMu` map             | Redis `notify:dedup:{key}` SETNX TTL          |
| 抽象        | `ports.Messenger`             | `notify.Service.Send(*Notification)`          |
