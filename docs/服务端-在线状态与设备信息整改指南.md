# 服务端在线状态与设备信息整改指南

> 目标读者：Go 服务端 AI Agent  
> 适用范围：`backend/`、`proto/antclaw/v1/system.proto`、`proto/antclaw/v1/device.proto`、`scripts/`  
> 当前目标：修复管理端无法正确看到 Android 客户端在线状态和设备信息的问题  
> 不处理范围：Web 端、Admin 前端体验重构

---

## 一、整改结论

当前服务端已经有基础能力：

- `AuthService.Login/Register` 会把 `ClientInfo.device_id` 写入 `devices` 表。
- `/sse/notifications` 会在客户端建立 SSE 后写入 `presence.Tracker`。
- `SystemService/GetOnlineUsers` 会读取 `presence.Tracker`。
- `DeviceService/ListDevices` 会从 `devices` 表查询设备并 JOIN 用户信息。

但实现存在几个会直接导致管理端数据不准的缺陷：

1. `DeviceService/ReportDeviceInfo` 不要求登录，且信任客户端传入的 `user_id`。
2. Android 当前不传 `user_id`，服务端会在 `ON CONFLICT` 更新时把 `user_id` 覆盖成 NULL。
3. `presence.Tracker` 用 `map[userID]OnlineUser`，同一用户多设备/多连接时，一个连接断开会把用户整体下线。
4. 在线状态是进程内内存状态，API 多实例部署时管理端只能看到当前进程连接，不能看到全局在线。
5. `GetOnlineUsers` 只补 `code_id`，没有补 `display_name`，管理端展示信息不完整。

本次整改必须把在线状态和设备信息链路做成可靠、可测试、可观测的生产路径。

## 三、P0 必修问题

### S-01：DeviceService 必须要求登录态

当前 `DeviceService` 注册时没有 auth interceptor：

```go
mux.Handle(antclawv1connect.NewDeviceServiceHandler(rpc.NewDeviceHandler(pgPool)))
```

问题：

- 任意请求都可以上报或删除设备。
- `ReportDeviceInfo` 信任客户端 `DeviceInfo.user_id`，存在越权覆盖风险。
- 管理端设备列表也没有权限控制。

整改要求：

1. `ReportDeviceInfo` 必须使用普通登录拦截器。
2. `DeleteDeviceInfo` 和 `ListDevices` 必须使用 Admin 拦截器，或拆成客户端/管理端两个服务。
3. Handler 内部从 `auth.Claims` / context 读取当前用户 ID，不使用客户端传入的 `DeviceInfo.user_id` 作为信任来源。

推荐短期注册方式：

```go
deviceHandler := rpc.NewDeviceHandler(pgPool)
mux.Handle(
    antclawv1connect.NewDeviceServiceHandler(
        deviceHandler,
        connect.WithInterceptors(auth.AuthInterceptor(true)),
    ),
)
```

但注意：这会让 `ListDevices/DeleteDeviceInfo` 对普通用户也可调用。更好的中期方案是拆分：

- `DeviceService.ReportDeviceInfo`：普通登录用户可调用。
- `AdminDeviceService.ListDevices/DeleteDeviceInfo`：管理员可调用。

如果暂不改 proto，Handler 内必须对 `ListDevices/DeleteDeviceInfo` 额外检查 admin role。

### S-02：ReportDeviceInfo 不能覆盖 user_id 为 NULL

当前代码：

```go
di.GetFingerprint(), strOrNil(di.GetUserId()),
```

Android 不传 `user_id`，因此 `strOrNil("")` 为 nil，SQL 更新时：

```sql
user_id=$15
```

会把 Login/Register 阶段写入的 `user_id` 覆盖成 NULL。

整改要求：

- `ReportDeviceInfo` 的 userID 必须来自 JWT 当前用户。
- SQL 中 `user_id` 永远写当前登录用户 ID。
- 如果短期拿不到 userID，也必须保留已有 `devices.user_id`，不能覆盖为 NULL。

推荐 SQL：

```sql
INSERT INTO devices (
  device_id, model, brand, os_version, os_type, app_version, build_number,
  screen_width, screen_height, network_type, timezone, locale, manufacturer, fingerprint, user_id
) VALUES (...)
ON CONFLICT (device_id) DO UPDATE SET
  model = EXCLUDED.model,
  brand = EXCLUDED.brand,
  os_version = EXCLUDED.os_version,
  os_type = EXCLUDED.os_type,
  app_version = EXCLUDED.app_version,
  build_number = EXCLUDED.build_number,
  screen_width = EXCLUDED.screen_width,
  screen_height = EXCLUDED.screen_height,
  network_type = EXCLUDED.network_type,
  timezone = EXCLUDED.timezone,
  locale = EXCLUDED.locale,
  manufacturer = EXCLUDED.manufacturer,
  fingerprint = EXCLUDED.fingerprint,
  user_id = EXCLUDED.user_id,
  updated_at = NOW()
```

如果需要防止设备被其他用户抢占，应先查询现有设备绑定：

- 未绑定：允许绑定当前用户。
- 已绑定当前用户：允许更新。
- 已绑定其他用户：返回 `connect.CodePermissionDenied`，除非产品允许设备迁移并记录审计。

### S-03：presence 必须支持多连接

当前 `Tracker`：

```go
users map[string]OnlineUser // userID -> OnlineUser
```

问题：

- 同一用户手机 + 平板同时在线，只保存最后一个连接。
- 任一连接断开时 `Unregister(userID)` 删除整个用户，另一个连接仍在线也会被管理端判离线。

整改目标：

```go
type Connection struct {
    ConnID      string
    UserID      string
    RemoteAddr  string
    UserAgent   string
    DeviceID    string
    ConnectedAt time.Time
    LastSeenAt  time.Time
}

type Tracker struct {
    users map[string]map[string]Connection // userID -> connID -> Connection
}
```

SSE 建连时：

- 生成 `connID`，建议 UUID 或 `userID + timestamp + random`。
- 从 header 或 query 记录 `device_id`，如果没有则为空。
- `Register(conn)`。

SSE 断开时：

- `Unregister(userID, connID)`。
- 只有该用户连接数为 0 时，管理端才显示离线。

`List()` 输出时：

- 每个用户聚合为一条，`connected_at` 取最早连接时间。
- 可扩展返回 `connection_count`、`device_count`、`last_seen_at`。

如果 proto 暂不加字段，也应先在服务端内部支持多连接，`GetOnlineUsersResponse.count` 统计在线用户数而不是连接数。

### S-04：GetOnlineUsers 补齐用户展示信息

当前只查询 `code_id`：

```sql
SELECT id::text, COALESCE(code_id, '') FROM users WHERE id::text = ANY($1)
```

整改为同时查询：

```sql
SELECT id::text, COALESCE(display_name,''), COALESCE(username,''), COALESCE(code_id,'')
FROM users
WHERE id::text = ANY($1)
```

并填充：

- `OnlineUserInfo.display_name`
- `OnlineUserInfo.code_id`

如果 proto 需要 username，可后续扩展字段。

### S-05：ListDevices 的 total 必须尊重过滤条件

当前 `ListDevices` 的列表支持 `os_type_filter`，但 total 永远：

```sql
SELECT COUNT(*) FROM devices
```

整改：

```sql
SELECT COUNT(*) FROM devices WHERE ($1='' OR os_type=$1)
```

同时补齐分页：

- 当前 proto 有 `cursor` 和 `next_cursor`，实现未使用。
- 如果管理端短期只需要第一页，可文档注明；但最好实现 `updated_at/device_id` 稳定游标。

## 四、P1 建议问题

### S-06：在线状态从进程内内存升级为 Redis Presence

当前 `presence.Tracker` 是单进程内存。多 API 实例时：

- 连接落在实例 A。
- 管理端请求落在实例 B。
- B 的 `presence.List()` 为空。

整改方案：

SSE 建连时写 Redis：

```text
presence:user:<userID>:conn:<connID> = JSON(Connection)
TTL = 45s
```

心跳每 15s 续期。

断开时删除 key。

`GetOnlineUsers` 扫描：

```text
SCAN presence:user:*:conn:*
```

聚合 userID。

短期如果部署只有单实例，可以先保留内存，但文档和 health/info 必须标明在线统计是单实例口径。

### S-07：SSE 鉴权失败与连接事件要可测

必须新增测试或 smoke：

- 无 token 访问 `/sse/notifications` 返回 401。
- 普通用户 token 访问后，`GetOnlineUsers` 能看到该用户。
- 断开 SSE 后，用户从在线列表移除。
- admin token 连接不计入客户端在线。
- 多连接同用户断开一个连接后仍在线。

### S-08：设备上报写入审计或日志

`AuthHandler.upsertDevice` 当前忽略 DB error：

```go
_, _ = h.pg.Exec(...)
```

建议：

- 不阻断登录，但必须 `log.Printf` 或 structured logger 记录错误。
- `ReportDeviceInfo` 成功/失败记录 device_id、user_id、os_type、app_version，不记录敏感 token。
- 设备被其他用户抢占时记录安全日志。

## 五、推荐实现顺序

### 第一步：修复设备 user_id 覆盖

这是管理端设备信息不准的最高优先级问题。

1. `DeviceService.ReportDeviceInfo` 接入认证。
2. 从 JWT 取当前 userID。
3. SQL 使用当前 userID，不再使用 `di.GetUserId()`。
4. 已绑定其他用户时返回 PermissionDenied。
5. 补单元测试。

### 第二步：修复 Android SSE 后，验证服务端 presence

服务端先保留内存 presence，但补多连接能力。

1. `Tracker.Register` 改为 connID 维度。
2. `userNotificationsSSE` 建连生成 connID。
3. `defer Unregister(userID, connID)`。
4. `GetOnlineUsers` 聚合用户并补 display_name/code_id。
5. 补测试。

### 第三步：完善 ListDevices

1. total 尊重 filter。
2. 实现 cursor 或明确短期无分页。
3. `ListDevices/DeleteDeviceInfo` 加 admin 权限。
4. 增加 e2e：登录 -> report device -> admin list devices。

### 第四步：Redis Presence

如果服务端未来多实例部署，必须做 Redis Presence。否则管理端在线统计仍会随机不准。

```text

```

1. 注册或登录测试用户，LoginRequest 带 `client.device_id=test-android-001`。

## 七、禁止事项

- 禁止 `ReportDeviceInfo` 信任客户端传入的 `user_id`。
- 禁止设备详情上报把已有 `devices.user_id` 覆盖成 NULL。
- 禁止普通用户调用管理端设备列表或删除接口。
- 禁止在线统计只用 `map[userID]` 覆盖多连接。
- 禁止为了管理端显示在线而伪造 presence。
- 禁止吞掉设备写入错误且不留日志。
- 禁止把 token、完整 Authorization header 写入日志。
