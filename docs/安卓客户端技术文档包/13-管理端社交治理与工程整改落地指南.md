## 一、整改目标

当前管理端已经具备登录、用户管理、设备管理、推送管理、审计日志、作业管理、数据源、策略、AI 配置和若干市场分析页面，但仍更接近“内部运维工具 + 数据分析入口”，尚未达到正式社交产品运营治理后台标准。

本轮整改目标：

```text
管理端从内部工具升级为运营治理后台
  -> 用户与权限边界清晰
  -> 社交内容可搜索、可审核、可处置、可追溯
  -> 高风险操作有确认、原因、审计和回滚路径
  -> 核心页面具备 loading/error/empty/retry 四态
  -> API、状态、表格、弹窗和权限模型可维护
  -> 测试与构建流程可支撑后续精简重构
```

---

## 二、AI Agent 必须遵守的硬约束

- 不允许新增 REST 业务调用；管理端 API 必须继续使用 `@connectrpc/connect-web` / Connect-RPC。
- 不允许用 `fetch()`、`axios` 或硬编码 demo 数据绕过真实 RPC。
- 不允许将后端错误静默吞掉并显示“空数据”。失败必须进入明确错误态。
- 不允许高风险操作无确认直接执行，包括封禁、解封、重置密码、全员推送、内容删除、内容隐藏、角色变更。
- 不允许仅靠前端隐藏按钮作为权限控制；后端必须兜底校验，前端只负责 UX 级可见性和禁用提示。
- 不允许在 `src/lib/api.ts` 继续堆叠新业务模块；新增功能必须按 feature 拆分 `api.ts`、`model.ts`、`hooks.ts`、`view.tsx`。
- 不允许在管理端新增合成统计作为真实业务指标；后端无数据时显示“暂无数据”或错误态。
- 涉及权限、安全、社交内容处置的改动必须先补测试或明确验收脚本。
- 不确定产品语义时在本文档标记“待确认”，不得自行猜测。

## 四、P0：上线前必须整改

### A13-P0-01：建立管理端权限上下文与路由/菜单/操作级权限

#### 问题描述

当前 `frontend/admin/src/App.tsx` 中 `PrivateRoute` 只检查 `localStorage.getItem('token')`，没有判断 token 是否过期、当前用户是否具备管理员角色，也没有页面级和按钮级权限模型。

#### 影响范围

- 管理端安全边界
- 多角色运营体系
- 高风险操作治理
- 用户、内容、推送、AI 配置等模块权限隔离

#### 改进方法

新增管理端认证与权限上下文：

```text
AuthProvider
  -> token / refresh 状态
  -> currentUser
  -> roles
  -> permissions
  -> expiresAt
  -> logout / refresh / requirePermission
```

权限至少覆盖：

```text
admin.users.read
admin.users.ban
admin.users.reset_password
admin.users.set_role
admin.social.read
admin.social.moderate
admin.social.delete
admin.push.send
admin.audit.read
admin.system.manage
admin.ai.manage
```

#### 可靠落地办法

1. 新增 `src/features/auth/AuthProvider.tsx`。
2. 新增 `src/features/auth/permissions.ts`。
3. `PrivateRoute` 改为读取 AuthContext，而不是直接读 localStorage。
4. `Layout` 菜单按权限过滤。
5. 高风险按钮增加 `RequirePermission` 包裹。
6. 服务端 Admin RPC 必须同步校验权限，不依赖前端。
7. 无权限时显示 `403` 页面或禁用按钮并展示原因。

#### 验收标准

- 无 token 访问管理端跳转登录。
- token 过期后触发刷新；刷新失败回登录。
- 非管理员访问管理端显示无权限页面。
- 无 `admin.push.send` 权限时看不到或不能点击推送发送按钮。
- 无 `admin.social.moderate` 权限时不能执行内容处置。
- 增加路由守卫和权限按钮测试。

### A13-P0-02：修复管理端 token 存储与刷新安全风险

#### 问题描述

当前登录后将 access token 与 refresh token 同时存入 localStorage。管理端权限高，一旦发生 XSS，攻击者可窃取长期凭据。

#### 影响范围

- 管理员账号安全
- 用户数据安全
- 内容治理权限
- 系统配置与 AI Secret 管理

#### 改进方法

优先目标：

```text
refresh token -> httpOnly Secure SameSite Cookie
access token  -> 内存态
```

如后端暂不支持 Cookie，短期至少做到：

```text
refresh token 不长期落 localStorage
access token 生命周期缩短
高危操作要求二次确认或 re-auth
增加 CSP
```

#### 可靠落地办法

1. 服务端增加管理端 refresh cookie 支持。
2. 前端 `transport.ts` 改为内存 token 管理。
3. `tryRefresh()` 捕获 ConnectError 并调用 refresh。
4. 刷新失败后清理内存状态并跳转登录。
5. 高危操作增加 re-auth 或二次确认。
6. 配置 CSP，禁止不可信脚本来源。

#### 验收标准

- refresh token 不再出现在 localStorage。
- access token 刷新成功后原请求可自动重试一次。
- refresh 失败跳转登录并清理状态。
- XSS 风险说明写入安全文档。
- 增加 token refresh 单飞测试。

### A13-P0-03：修正 Connect-RPC 认证错误处理逻辑

#### 问题描述

当前 `src/lib/transport.ts` 中通过检查 response 上的 `(res as any).code === 'unauthenticated'` 触发 refresh。Connect-RPC Web 错误通常以 `ConnectError` 抛出，这种写法可能无法可靠捕获 401/Unauthenticated。

#### 影响范围

- 登录态续期
- 所有管理端 RPC
- 页面错误态
- 用户体验

#### 改进方法

在 interceptor 中捕获 `ConnectError`：

```text
try next(req)
catch ConnectError(Code.Unauthenticated)
  -> single-flight refresh
  -> refresh 成功后重试原请求一次
  -> refresh 失败清 session
```

#### 可靠落地办法

1. 从 `@connectrpc/connect` 引入 `ConnectError`、`Code`。
2. 在 catch 分支判断 `e instanceof ConnectError && e.code === Code.Unauthenticated`。
3. 防止无限重试：每个请求最多 retry 一次。
4. refresh 接口使用无认证 transport。
5. 所有失败必须继续 throw 给页面，由页面展示错误态。

#### 验收标准

- mock 首次 `Unauthenticated`、refresh 成功，原请求成功。
- mock refresh 失败，跳转登录。
- mock 非认证错误，不触发 refresh。
- 并发多个 401 时只发起一次 refresh。

### A13-P0-04：补齐社交内容治理后台

#### 问题描述

当前管理端没有真正的社交内容治理模块。`CryptoSocialPage` 是外部加密社交情绪数据，不是 AntClaw 自身帖子、评论、点赞、分享和举报治理。

#### 影响范围

- 违规内容处理
- 社区运营
- 用户争议处理
- 法务与合规
- 内容安全

#### 改进方法

新增社交治理功能组：

```text
社交治理
  -> 帖子管理
  -> 评论管理
  -> 举报审核
  -> 用户社交画像
  -> 圈子管理（后端支持后）
  -> 处置记录
```

#### 可靠落地办法

1. 前端新增 `src/features/social-admin/`。
2. 服务端新增或扩展 Admin RPC，而不是让前端直接调用普通用户 Feed RPC 执行管理动作。
3. 新增帖子列表接口，支持分页、关键词、作者、时间、visibility、状态筛选。
4. 新增评论列表接口，支持按帖子、作者、时间、状态筛选。
5. 新增内容处置接口：隐藏、恢复、删除、降权、置顶、取消置顶。
6. 所有处置必须记录原因、管理员 ID、时间和审计日志。

#### 验收标准

- 管理端可分页查看帖子列表。
- 可按作者、内容关键词、时间、状态筛选。
- 可查看帖子详情和评论。
- 可隐藏/恢复帖子，操作必须填写原因。
- 可删除评论，操作必须填写原因。
- 处置动作写入审计日志。
- 无权限用户不能查看或执行社交处置。

### A13-P0-05：补齐举报与审核工作流

#### 问题描述

当前没有举报队列、审核状态、处理人、复核、申诉和处理闭环。社交产品上线后无法规模化治理违规内容。

#### 影响范围

- 内容安全
- 审核效率
- 用户信任
- 合规风险

#### 改进方法

新增审核工单模型：

```text
ModerationCase
  -> case_id
  -> source(report/auto/manual)
  -> target_type(post/comment/user/message)
  -> target_id
  -> reporter_id
  -> reason
  -> priority
  -> status
  -> assignee_id
  -> reviewer_id
  -> notes
  -> actions
  -> created_at / updated_at
```

状态流：

```text
pending -> in_review -> actioned / rejected -> appealed -> closed
```

处置动作：

```text
忽略举报
隐藏内容
删除内容
警告用户
限制发帖
临时封禁
永久封禁
升级复核
```

#### 可靠落地办法

1. 服务端新增 moderation proto 和表结构。
2. 前端新增举报队列页面。
3. 前端新增审核详情页。
4. 支持分派处理人、优先级、备注。
5. 审核动作必须生成审计记录。
6. 对用户处罚必须同步通知用户。

#### 验收标准

- 可查看待审核举报列表。
- 可按状态、优先级、类型、处理人筛选。
- 可进入详情查看目标内容、举报原因和上下文。
- 可执行审核动作并填写原因。
- 可分派处理人。
- 审核动作写入审计日志并更新状态。
- 单元测试覆盖状态流转和权限校验。

### A13-P0-06：高风险操作必须增加确认、原因与审计闭环

#### 问题描述

当前 `Users.tsx` 中封禁、解封、密码重置、CodeID 重置等操作确认不足。`PushManagement.tsx` 中“不选择任何用户 = 推送给全部在线用户”也存在误发风险。

#### 影响范围

- 用户账号安全
- 社区运营事故
- 推送误发
- 审计追责

#### 改进方法

所有高风险操作统一流程：

```text
点击操作
  -> 确认弹窗
  -> 填写原因 / 范围 / 有效期
  -> 二次确认
  -> 执行 RPC
  -> 显示结果
  -> 审计日志可追踪
```

#### 可靠落地办法

1. 新增通用 `DangerConfirmDialog`。
2. 封禁必须填写原因，可选择过期时间。
3. 密码重置必须二次输入确认。
4. 全员推送必须显示目标范围、标题、正文预览。
5. 角色变更必须显示变更前后差异。
6. 后端审计日志必须记录原因字段。

#### 验收标准

- 不能一键封禁用户。
- 封禁原因为空时不能提交。
- 全员推送必须二次确认。
- 密码重置必须确认目标用户。
- 审计日志可看到操作者、目标、原因、时间。

### A13-P2-02：替换无 backoff 的定时轮询

#### 问题描述

`PushManagement.tsx` 和 `Devices.tsx` 使用 `setInterval` 定时刷新，失败时无 backoff，也不感知页面可见性。

#### 改进方法

优先使用 server-streaming 或 SSE；短期可抽象 `usePolling`：

```text
interval
backoff
pauseWhenHidden
manualRefresh
lastUpdated
errorCount
```

#### 验收标准

- 轮询失败不会无限高频请求。
- 页面隐藏时暂停非必要刷新。
- UI 显示最后更新时间。
- 刷新失败显示错误提示。
