# 服务端社交板块整改落地指南

> 适用范围：`backend/internal/service/feed`、`backend/internal/service/trader`、`backend/internal/infra/postgres/*social*`、`backend/internal/adapter/rpc/alfq_*`、`proto/antclaw/v1/alfq_*.proto`  
> 目标读者：服务端 AI Agent  
> 来源：2026-05-17 服务端社交板块技术与架构审查  
> 关系：本文件补充 `09-服务端配套改造优化文档.md`、`10-X-Threads社交客户端落地指导.md`、`11-安卓客户端二次审查整改落地指南.md`。

---

## 一、整改目标

服务端社交板块已经具备 Feed、帖子、评论、点赞、分享、交易员主页、关注、搜索、趋势等基础能力，但仍存在互动闭环、隐私安全、内容安全、性能扩展、接口规范、日志可观测性等方面的设计缺口。

本轮整改目标：

```text
社交核心链路可靠
  -> 互动事件可通知、可审计
  -> 隐私边界不穿透
  -> 写操作有限流和内容约束
  -> Feed/Search/Trend 可扩展
  -> RPC 权限语义清晰
  -> 错误、日志、测试可治理
```

---

## 二、AI Agent 必须遵守的硬约束

- 不允许引入硬编码假数据作为 fallback。
- 不允许将非法隐私参数静默降级为公开状态。
- 不允许新增 REST 业务路由；对外接口继续使用 Connect-RPC。
- 不允许 Handler 直接写业务 SQL；保持 Handler -> Service -> Repository。
- 修改 proto 后必须执行 `buf generate`，并同步更新 handler、测试和文档。
- 涉及隐私、安全、权限的改动必须优先写测试。
- 不确定产品语义时先在文档中标记“待确认”，不得自行猜测。

## 三、P0：上线前必须整改

### S12-P0-01：修正发帖可见性校验，禁止非法值默认公开

#### 问题描述

当前 `CreatePost` 中非法 `visibility` 会被静默改为 `public`。如果客户端传错值，用户可能以为内容受限，实际被公开发布。

#### 影响范围

- 发帖隐私
- 用户信任
- 客户端兼容
- 法务和合规风险

#### 改进方法

可见性字段必须严格校验：

```text
public     -> 允许
followers  -> 允许
circle     -> 当前未支持则明确 InvalidArgument
其他值      -> InvalidArgument
```

#### 可靠落地办法

1. 在 `feed.Service.CreatePost` 中新增 `validateVisibility`。
2. 非法值返回 `connect.CodeInvalidArgument`。
3. `circle` 在圈子权限未完成前继续返回明确错误。
4. 不允许把未知值降级成 `public`。
5. 如果未来支持 `circle`，必须校验 `circle_id` 存在且当前用户是成员。

#### 验收标准

- 传空 visibility 时按产品默认值处理，建议默认为 `public`。
- 传 `followers` 可成功创建粉丝可见帖子。
- 传 `circle` 返回明确未支持错误。
- 传任意未知值返回 `InvalidArgument`。
- 增加 `TestCreatePost_InvalidVisibilityDoesNotBecomePublic`。

### S12-P0-02：禁止邮箱作为公开展示名或搜索结果

#### 问题描述

当前多个查询使用 `COALESCE(display_name, email)`，搜索还支持 `email ILIKE`。这会导致用户邮箱出现在 Feed 作者名、搜索结果、关注列表、资料页等公开场景。

#### 影响范围

- 用户隐私
- 搜索结果
- Feed 作者展示
- 关注/粉丝列表
- 交易员主页

#### 改进方法

公开社交场景只能展示安全公开名称：

```text
display_name 非空 -> display_name
username/code_id 非空 -> username/code_id
否则 -> 匿名交易员 / User-短ID
```

搜索不得匹配邮箱，除非是用户本人私有能力或管理员能力。

#### 可靠落地办法

1. 梳理所有 `COALESCE(display_name, email)`。
2. 新增统一 SQL 表达式或 Repository helper，例如 `publicDisplayNameExpr`。
3. `SearchUsers` 删除 `email ILIKE` 条件。
4. Feed 作者名、评论作者名、UserInfo、TraderProfile 全部使用公开展示名。
5. 如需要兼容老数据，创建后台脚本为缺失 display_name 的用户生成安全 fallback。

#### 验收标准

- 搜索任意邮箱片段不会返回用户。
- Feed、评论、关注列表、资料页不显示邮箱。
- 单元测试覆盖无 display_name 用户的展示名 fallback。

### S12-P0-03：补齐内容长度、类型和字段校验

#### 问题描述

当前发帖和评论只检查空字符串，缺少长度、空白、枚举、signal 字段等校验。

#### 影响范围

- 发帖
- 评论
- 分享
- 搜索
- 趋势聚合
- 数据库存储
- 客户端渲染性能

#### 改进方法

建立统一内容校验规则：

```text
post.content      建议 1..2000 字符
comment.content   建议 1..1000 字符
share.comment     建议 0..1000 字符
post_type         text / signal_card / chart_share / share
visibility        public / followers / circle(未支持则拒绝)
signal_confidence 0..100
```

具体数值如产品文档未定义，先在本文件记录默认值，并允许后续产品修订。

#### 可靠落地办法

1. 新增 `internal/service/feed/validation.go`。
2. 实现 `ValidateCreatePostRequest`、`ValidateCommentRequest`、`ValidateSharePostRequest`。
3. 使用 `strings.TrimSpace` 判断有效内容。
4. 超长内容返回 `InvalidArgument`。
5. 非法 `post_type`、`signal_direction`、`signal_confidence` 返回 `InvalidArgument`。
6. 测试覆盖空白、超长、非法类型、非法 signal 字段。

#### 验收标准

- 纯空白发帖/评论失败。
- 超长内容失败。
- 非法 `post_type` 不入库。
- 非法 signal card 不入库。
- 所有失败返回 Connect `InvalidArgument`。

### S12-P0-04：为社交写操作增加限流和防刷保护

#### 问题描述

发帖、评论、点赞、关注、分享缺少频率限制。恶意用户可快速制造垃圾内容和数据库压力。

#### 影响范围

- Feed 写入
- 评论区
- 关注关系
- 点赞互动
- 数据库稳定性
- 社区安全

#### 改进方法

为社交写操作加入基于用户维度的 Redis 限流：

```text
CreatePost      user + action
CommentOnPost   user + action + post
SharePost       user + action
LikePost        user + action
Follow          user + action
```

#### 可靠落地办法

1. 在 service 层引入 `SocialRateLimiter` 接口。
2. Redis 实现放在 infra 或 service 子包，不要在 Handler 里写限流。
3. 限流失败返回 `ResourceExhausted`。
4. 测试中提供 fake limiter。
5. 默认阈值如文档未定义，先使用保守默认并在文档中写明：
   - 发帖：每分钟 5 次
   - 评论：每分钟 20 次
   - 点赞：每分钟 60 次
   - 关注：每分钟 20 次
   - 分享：每分钟 10 次

#### 验收标准

- 超限写操作返回 `connect.CodeResourceExhausted`。
- 限流 key 包含 user id 和 action。
- Redis 异常时采用 fail-closed 还是 fail-open 必须文档化；默认建议关键写操作 fail-closed。
- 增加限流单元测试。

### S12-P0-05：补齐评论、关注、分享的通知闭环

#### 问题描述

当前评论、关注、分享不会产生通知，也没有社交事件流。用户无法感知互动。

#### 影响范围

- 通知中心
- SSE/Stream 实时推送
- 用户留存
- 社交反馈

#### 改进方法

社交写操作成功后发布领域事件：

```text
PostCommented
PostShared
UserFollowed
PostLiked(是否通知按产品策略，可先只审计不推送)
```

事件由通知服务消费，写入通知表并推送实时事件。

#### 可靠落地办法

1. 在 service 层定义 `SocialEventPublisher` 接口。
2. Feed/Trader Service 只发布领域事件，不直接拼通知 DB 结构。
3. 通知服务根据事件创建通知。
4. 自己对自己的帖子评论/分享不通知自己。
5. 对不可见内容不产生跨权限通知。
6. 事件发布失败不得导致数据库写入回滚，但必须记录结构化错误日志。

#### 验收标准

- 评论他人帖子后，帖子作者收到通知。
- 分享他人帖子后，原作者收到通知。
- 关注他人后，被关注者收到通知。
- 自己操作自己的内容不产生无意义通知。
- 测试覆盖事件发布成功、发布失败降级。

---

### S12-P0-06：建立社交 RPC 权限矩阵并修正注册注释

#### 问题描述

`rpc.go` 注释写着 `Auth-required social`，但 Feed、Trader、Search、Trend 并没有全部使用强认证拦截器。当前实际是“读可匿名、写在 service 层检查登录”的混合模型。

#### 影响范围

- 安全边界
- 后续 RPC 开发
- 客户端接入
- 审计和测试

#### 改进方法

建立明确权限矩阵：

| Service/RPC | 匿名访问 | 登录要求 | 说明 |
|---|---:|---:|---|
| Feed.GetFeed | 是 | 否 | 匿名只看 public |
| Feed.GetPost | 是 | 否 | 匿名只看 public |
| Feed.CreatePost | 否 | 是 | 写操作 |
| Feed.LikePost | 否 | 是 | 写操作 |
| Feed.CommentOnPost | 否 | 是 | 写操作 |
| Trader.GetProfile | 是 | 否 | 公开资料 |
| Trader.Follow | 否 | 是 | 写操作 |
| Search.Search | 是 | 否 | 仅公开数据 |
| Trend.* | 是 | 否 | 仅公开聚合 |
| Notification.* | 否 | 是 | 用户私有数据 |

#### 可靠落地办法

1. 更新 `rpc.go` 注释为 `Social services: mixed public/read and auth-required/write`。
2. 每个写操作在 service 层必须检查 userID。
3. 每个读操作必须根据 userID 过滤可见性。
4. 为每个写 RPC 增加 unauthenticated 测试。
5. 为匿名读接口增加隐私过滤测试。

#### 验收标准

- 注释、文档、测试与代码权限策略一致。
- 新增 RPC 时必须同步更新权限矩阵。

## 四、P1：性能、体验与一致性整改

### S12-P1-01：Feed 计数从逐行子查询改为可扩展统计模型

#### 问题描述

Feed 列表每条帖子都通过子查询计算 like/comment/share count，数据量增长后会成为慢查询。

#### 改进方法

引入 `alfq_post_stats` 或等价统计机制：

```text
post_id
like_count
comment_count
share_count
updated_at
```

#### 可靠落地办法

1. 新增 migration 创建统计表。
2. 写操作成功后同步或异步更新统计。
3. Feed 查询 JOIN 统计表读取计数。
4. 初始迁移脚本回填历史计数。
5. 保留定期校准任务修复计数漂移。

#### 验收标准

- Feed 查询不再对每条帖子执行 3 个 count 子查询。
- 点赞/取消点赞后计数准确。
- 评论/分享后计数准确。
- 有统计回填 SQL 或脚本。

### S12-P1-02：搜索改造为可索引方案

#### 问题描述

搜索使用 `ILIKE '%query%'`，无法随数据量扩展，并且存在邮箱匹配隐私问题。

#### 改进方法

短期使用 PostgreSQL `pg_trgm` + GIN 索引；中长期可抽象到独立搜索服务。

#### 可靠落地办法

1. 新增 migration：启用 `pg_trgm`。
2. 为 `users.display_name`、`alfq_posts.content` 建 GIN trigram 索引。
3. 设置最小搜索长度，例如 2 或 3。
4. 删除 email 搜索。
5. 搜索结果只返回 public 内容和公开用户字段。

#### 验收标准

- 空 query 或过短 query 返回 `InvalidArgument`。
- 搜索不返回 followers/circle 内容。
- 搜索不匹配邮箱。
- 有 repository 测试或集成测试覆盖隐私过滤。

### S12-P1-03：趋势接口增加预聚合与缓存

#### 问题描述

趋势接口实时扫描帖子和互动表，随着数据增长会拖慢数据库。

#### 改进方法

按窗口预聚合趋势数据：

```text
trend_topics(window, topic, post_count, engagement_count, calculated_at)
hot_symbols(window, symbol, post_count, signal_count, engagement_count, calculated_at)
```

#### 可靠落地办法

1. 新增趋势聚合表。
2. 新增 worker 或定时任务每 1-5 分钟刷新。
3. API 优先读预聚合表。
4. Redis 对结果加短 TTL 缓存。
5. 聚合失败时返回上一次成功结果，并记录 stale 标记。

#### 验收标准

- Trend API 不再每次实时 count likes/comments/shares。
- 趋势接口响应时间稳定。
- 聚合任务失败时 API 不报 500，除非没有任何历史结果。

### S12-P1-04：补齐 Profile 字段落库与隐私控制

#### 问题描述

`UpdateProfileRequest` 有 bio 和交易表现展示开关，但当前实现只更新 display_name，profile 读取也返回固定 false 和 0。

#### 改进方法

建立用户社交资料表或扩展现有 users 表：

```text
bio
show_win_rate
show_profit_factor
show_sharpe
show_total_trades
```

交易表现字段必须根据用户开关返回。

#### 可靠落地办法

1. 新增 migration 创建/扩展 profile 字段。
2. `UpdateProfile` 写入 display_name、bio、show flags。
3. `GetProfile` 按 show flags 决定是否返回交易指标。
4. 如交易指标来源尚未定义，返回 0 但 show flag 必须真实保存。
5. 更新 proto 文档说明字段来源。

#### 验收标准

- 更新 bio 后再次 GetProfile 可读到。
- show flags 可保存和读取。
- 未开启展示时交易指标不返回真实值。
- 增加 `TestUpdateProfile_AllFieldsPersisted`。

### S12-P1-05：完善 followers Feed 与关注内容体验

#### 问题描述

`GetFeed` 只返回 public 内容，followers-only 内容不会出现在普通首页 Feed 中。

#### 改进方法

明确区分 Feed 类型：

```text
public/recommended feed -> public only
following feed          -> followed users 的 public + followers-only
profile posts           -> 按访问者身份过滤
```

#### 可靠落地办法

1. 如果客户端有关注 Tab，则提供明确 RPC 或 filter。
2. `GetFollowingFeed` 应作为正式 RPC 暴露，或通过 `GetFeed.filter=following` 实现。
3. followers-only 内容只对作者本人和粉丝可见。
4. 测试覆盖匿名、粉丝、非粉丝、作者四类访问者。

#### 验收标准

- 粉丝能在关注流看到 followers-only 内容。
- 非粉丝不能在任何入口看到 followers-only 内容。
- 作者能看到自己的所有内容。

### S12-P1-06：评论回复结构补齐

#### 问题描述

评论支持 `parent_comment_id`，但列表仍是平铺，缺少回复树能力。

#### 改进方法

短期保留平铺但返回 parent 信息；中期新增按父评论获取回复的 RPC。

#### 可靠落地办法

1. `ListComments` 明确只返回一级评论，或明确平铺语义。
2. 新增 `ListCommentReplies` 时需支持 cursor。
3. 评论计数区分总数和一级评论数，如产品需要。
4. 回复必须校验父评论属于同一帖子。

#### 验收标准

- 父评论不属于当前帖子时返回 `InvalidArgument`。
- 回复列表可分页。
- 客户端可根据返回结构稳定展示楼中楼。

## 五、P2：架构治理与长期扩展

### S12-P2-01：调整 Service 与 Repository 边界

#### 问题描述

当前 Service 直接依赖 `infra/postgres` 包中的 Repository 接口、Row 类型和 Cursor 工具，削弱分层边界。

#### 改进方法

将 Repository 接口和领域模型上移到 service/domain 边界，infra/postgres 只负责实现。

#### 可靠落地办法

1. 在 `internal/service/feed` 定义 `Repository` 接口和领域 row/model。
2. `infra/postgres` 实现该接口。
3. Cursor 可移到 service/shared 或 domain/social 包。
4. 先小步迁移 Feed，再迁移 Trader/Search/Trend。
5. 保证 handler 不受影响。

#### 验收标准

- `service/feed` 不再 import `internal/infra/postgres`。
- 单元测试 fake repo 更简单，不依赖 Postgres row 类型。
- 无循环依赖。

---

### S12-P2-02：建立结构化日志、指标和审计事件

#### 问题描述

社交 service 使用 `log.Printf`，缺少 request id、user id、post id、latency、错误码等结构化信息。

#### 改进方法

统一社交可观测性：

```text
structured log
metrics
business audit/event
```

#### 可靠落地办法

1. 引入项目现有 logger 或新增统一 logger 接口。
2. 社交写操作记录业务事件：post_created、comment_created、post_liked、user_followed、post_shared。
3. RPC 层或 interceptor 记录 method、latency、code。
4. 错误日志必须带 user_id、post_id、action。
5. 隐私字段不得进入日志，例如 email、token、内容全文。

#### 验收标准

- `log.Printf` 从 feed/trader service 中移除或降到极少。
- 关键写操作有审计事件。
- 线上可按 post_id/user_id 排查问题。

---

### S12-P2-03：Proto 字段从 string 收敛为 enum 或严格校验

#### 问题描述

`post_type`、`visibility`、`signal_direction`、`tier` 等使用 string，容易出现拼写错误和兼容问题。

#### 改进方法

优先新增 enum；如因兼容暂不改 proto，则服务端必须严格校验 string。

#### 可靠落地办法

1. 新 proto 可增加 enum 字段，保留旧 string 字段一段兼容期。
2. 新客户端优先使用 enum。
3. 服务端同时支持旧字段和新字段时，冲突必须返回 `InvalidArgument`。
4. 更新 buf generate。

#### 验收标准

- 非法枚举不会入库。
- proto 文档明确每个枚举含义。
- 旧客户端兼容策略有测试。

---

### S12-P2-04：拆分不同语义的 Cursor 类型

#### 问题描述

推荐交易员将 follower count 塞进 `SocialCursor.CreatedAt`，造成语义混乱。

#### 改进方法

为不同排序定义不同 cursor：

```text
TimeIDCursor          -> created_at + id
CountIDCursor         -> count + id
ScoreIDCursor         -> score + id
```

#### 可靠落地办法

1. 保留旧 cursor 解码兼容当前客户端。
2. 新增内部 cursor 类型和编码方法。
3. 推荐交易员改用 `CountIDCursor`。
4. Feed 和评论继续使用 `TimeIDCursor`。

#### 验收标准

- Cursor 字段语义不再混用。
- 推荐交易员分页稳定。
- 老 cursor 兼容测试通过。

### S12-P2-05：统一 migration 路径与 schema 治理

#### 问题描述

当前存在多套社交 migration 路径，容易造成不同环境 schema 不一致。

#### 改进方法

明确唯一权威 migration 路径，并建立 schema 验证。

#### 可靠落地办法

1. 梳理 `backend/internal/postgres/migrations` 与 `backend/internal/adapter/storage/postgres/migrations` 的执行关系。
2. 明确哪个目录是生产权威路径。
3. 对重复 migration 写归档说明，避免后续 Agent 继续双写。
4. 新增 schema smoke test，检查关键字段和索引存在。

#### 验收标准

- 新环境初始化后存在 `original_post_id`、`parent_comment_id` 和关键 cursor 索引。
- 文档明确新增 migration 应放在哪里。
- CI 或脚本能检测 schema 缺失。

### S12-P2-06：补齐编辑、删除、软删除和举报模型

#### 问题描述

当前缺少删除、编辑、软删除、举报、屏蔽、静音等社区治理能力。

#### 改进方法

先做最小治理模型：

```text
post.status: active/deleted/hidden/moderated
comment.status: active/deleted/hidden/moderated
reports: target_type, target_id, reporter_id, reason, status
blocks: blocker_id, blocked_id
mutes: muter_id, muted_id
```

#### 可靠落地办法

1. 新增 proto 和 migration 前先写设计文档。
2. 列表查询默认过滤 deleted/hidden/moderated。
3. 作者可删除自己的 post/comment。
4. 管理端可隐藏/恢复违规内容。
5. block 后互相不可互动，mute 后不进入信息流。

#### 验收标准

- 删除后列表不可见，详情按权限返回 deleted 状态或 NotFound。
- 被 block 用户无法关注、评论、互动。
- 举报记录可追踪。
