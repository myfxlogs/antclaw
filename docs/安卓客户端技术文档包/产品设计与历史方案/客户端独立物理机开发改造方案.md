# 客户端独立物理机开发改造方案

## 一、问题背景

当前 AntClaw 的后端、协议、生成代码与 Android 客户端位于同一仓库内。单机开发时路径、端口、生成代码和环境变量都能直接共享；但当 Android 客户端复制到另一台物理机独立开发时，会出现以下问题：

- 客户端不知道应该连接哪一个后端地址。
- `localhost` 在 Android 模拟器、真机、后端服务器上含义不同。
- 客户端依赖 proto / 生成代码，但另一台机器未必有完整后端仓库。
- 后端 proto 变更后，客户端无法稳定同步协议版本。
- SSE、Connect-RPC、JWT、证书、网关路径在不同环境下容易不一致。
- 后端和客户端必须放在一起才能编译或联调，降低协作效率。

本方案目标是把当前“同仓强耦合开发”改造成“Android 客户端只依赖 `https://api.alfq.org/` 这一稳定 API 入口，即可在另一台物理机独立开发、独立构建、独立联调”的模式。

## 二、改造目标

### 2.1 必须达到的能力

Android 客户端在另一台物理机上应能独立完成：

- 拉取客户端代码。
- 配置后端环境地址。
- 编译 Debug / Release 包。
- 调用 Connect-RPC 接口。
- 建立 `/sse/notifications` 通知长连接。
- 登录、刷新 token、查看通知、接收推送。
- 在后端 proto 更新后可明确同步协议版本。

### 2.2 不应再依赖的条件

独立开发时 Android 客户端不应依赖：

- 后端源码必须在同一台机器。
- Docker Compose 必须在客户端机器上运行。
- 本地固定路径 `/opt/antclaw/backend`、`/opt/antclaw/proto`、`/opt/antclaw/gen`。
- 开发者手工复制生成代码。
- 使用 Docker 内部服务名访问后端，例如 `antclaw-api:8080`。

## 三、当前主要耦合点

### 3.1 后端地址硬编码

当前 Android 客户端在：

```text
frontend/android/app/build.gradle.kts
```

存在固定后端地址：

```kotlin
buildConfigField("String", "BASE_URL", "\"https://api.alfq.org/\"")
```

客户端网络层读取：

```text
frontend/android/app/src/main/java/com/antclaw/alfq/data/rpc/ConnectTransportProvider.kt
```

其中：

```kotlin
val baseUrl: String = BuildConfig.BASE_URL
```

问题：

- 只能连接一个固定环境。
- 无法区分本地、局域网、测试、预发、生产。
- 另一台物理机开发时必须改代码才能切环境。

### 3.2 协议与生成代码耦合

AntClaw 对外接口定义在：

```text
proto/antclaw/v1/*.proto
```

生成代码在：

```text
gen/
```

Android 独立开发时，如果没有协议分发机制，会出现：

- 客户端不知道当前后端兼容哪个 proto 版本。
- 后端改 proto 后，客户端编译失败或运行时字段不一致。
- 多台机器手工复制 `gen` 容易产生版本漂移。

### 3.3 SSE 与移动端环境耦合

后端个人通知入口为：

```text
/sse/notifications
```

移动端需要注意：

- Android 不能直接使用 Web `EventSource`。
- 后台运行时长连接可能被系统断开。
- 真机访问开发机不能使用 `localhost`。
- HTTPS 证书、反向代理、JWT Header 必须统一。

### 3.4 登录态耦合

当前 `ConnectTransportProvider` 通过 token provider 注入：

```kotlin
.header("Authorization", "Bearer $token")
```

独立开发时必须明确：

- token 从哪里保存。
- 401 后如何退出或刷新。
- SSE 与 RPC 是否使用同一 token。
- 不同环境 token 是否隔离。

## 四、推荐总体架构

### 4.1 后端作为远程 API 服务

Android 客户端物理机不运行完整后端，只访问唯一 API 根地址：

```text
https://api.alfq.org/
```

当前域名链路已验证：

| 检查项 | 请求 | 结果 | 结论 |
|---|---|---|---|
| API 根路径 | `GET https://api.alfq.org/` | `404 page not found` | 正常，根路径没有业务路由 |
| 健康检查 | `POST https://api.alfq.org/antclaw.v1.SystemService/Healthz` | `200 healthy` | Cloudflare 到 `antclaw-api` 链路正常 |
| SSE 鉴权 | `GET https://api.alfq.org/sse/notifications` | `401 unauthorized` | SSE 路径可达，鉴权正常生效 |

最终访问链路：

```text
Android 客户端
  → https://api.alfq.org/
  → Cloudflare Tunnel
  → cloudflared
  → http://localhost:8082
  → antclaw-api 容器 8080
  → PostgreSQL / Redis / Worker
```

### 4.2 域名职责划分

长期按域名职责分层，不混用管理端域名与客户端 API 域名：

| 域名 | 职责 | 后端目标 | 客户端是否使用 |
|---|---|---|---|
| `https://api.alfq.org/` | 客户端 API、Connect-RPC、SSE | `http://localhost:8082` | 是 |
| `https://ad.alfq.org/` | 管理端 Web | `http://localhost:8081` | 否 |

约定：

- Android `BASE_URL` 固定使用 `https://api.alfq.org/`。
- Android 不访问 `https://ad.alfq.org/`。
- Android 不访问 `:8082`、`:8081` 等非标准端口。
- Cloudflare Tunnel 负责把 `api.alfq.org` 转发到宿主机 `localhost:8082`。
- 所有 Connect-RPC 与 SSE 都走同一个 API 根域名。

## 五、后端改造方案

### 5.1 暴露稳定外部入口

后端必须提供客户端可访问的统一入口：

```text
https://api.alfq.org/
```

必须支持：

- Connect-RPC POST 请求。
- `/sse/notifications`。
- `Authorization: Bearer <token>`。
- HTTPS。
- 健康检查端点。

建议新增或确认：

```text
GET /healthz
POST /antclaw.v1.SystemService/Healthz
GET /sse/notifications
```

### 5.2 Cloudflare Tunnel 与网关要求

当前采用 Cloudflare Tunnel 后，公网侧不需要直接开放 `8082`。Tunnel Public Hostname 应保持：

```text
api.alfq.org → http://localhost:8082
ad.alfq.org  → http://localhost:8081
```

Cloudflare / Gateway 必须：

- 保留 `Authorization` Header。
- SSE 关闭缓冲：`X-Accel-Buffering: no`。
- SSE 设置长超时。
- 支持 HTTP/2 客户端访问。
- 不缓存 Connect-RPC POST。
- 不重写 Connect-RPC 路径。
- 不启用 Cloudflare Access 保护 `api.alfq.org`，避免 Android 被额外登录层拦截。
- 可对 `ad.alfq.org` 启用 Cloudflare Access，因为它是管理端。

SSE 推荐代理参数：

```nginx
proxy_buffering off;
proxy_cache off;
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
```

### 5.3 客户端唯一后端地址

客户端在任何物理机开发时，都统一使用：

```text
https://api.alfq.org/
```

不再要求客户端开发机与后端开发机处于同一局域网，也不要求客户端机器运行 Docker Compose。

禁止让 Android 客户端访问 Docker 内部域名：

```text
antclaw-api:8080
postgres:5432
redis:6379
```

客户端只能访问 API 网关，不直接访问数据库或 Redis。

## 六、Android 客户端改造方案

### 6.1 改造 BASE_URL 配置

将当前单一硬编码：

```kotlin
buildConfigField("String", "BASE_URL", "\"https://api.alfq.org/\"")
```

改为固定使用客户端 API 专用域名：

```kotlin
buildConfigField("String", "BASE_URL", "\"https://api.alfq.org/\"")
```

如果后续确实需要测试环境，也应使用同类 API 专用域名，例如 `https://api-staging.alfq.org/`，而不是让客户端直接访问端口。

要求：

- README 写明当前唯一 API 根地址。
- App Debug 信息页显示当前 `BASE_URL`，便于排查。
- Release 包禁止出现 `http://`、`:8082`、`:8081` 等直连地址。

### 6.2 ConnectTransportProvider 改造

当前：

```kotlin
val baseUrl: String = BuildConfig.BASE_URL
```

建议增强：

- 统一 normalize base URL，保证末尾 `/`。
- Debug 下打印当前 base URL。
- 401 时通知 AuthManager 清理 token。
- OkHttp 设置合理超时。
- SSE 与 RPC 共用 token provider。

推荐规则：

```text
BASE_URL 必须是 API 根地址：`https://api.alfq.org/`
RPC 路径由 Connect 客户端拼接。
SSE 路径为 BASE_URL + sse/notifications。
```

### 6.3 Android SSE 客户端

建议新增：

```text
frontend/android/app/src/main/java/com/antclaw/alfq/data/notification/NotificationSseClient.kt
```

职责：

- 使用 OkHttp 建立 `GET /sse/notifications`。
- Header 注入 `Authorization: Bearer <token>`。
- 解析 `event: notification` 与 `data:`。
- 忽略 `: ping`。
- 前台启动，后台断开。
- 断线指数退避重连。
- 401 立即停止并通知重新登录。

### 6.4 本地缓存与离线补偿

客户端不应依赖 SSE 永久在线。

流程：

```text
App 进入前台
  → 调用 UnreadCount
  → 调用 ListUnread
  → 刷新本地 Room 缓存
  → 建立 SSE
```

这样即使后台断线，也能通过未读列表补齐。

## 七、协议分发改造方案

### 7.1 推荐方案：生成 Android 协议包

为了让 Android 独立物理机开发，不应要求客户端开发者持有完整后端源码。

推荐把 proto 生成代码发布为内部 Maven 包：

```text
com.antclaw:proto-android:<version>
```

Android 依赖：

```kotlin
implementation("com.antclaw:proto-android:0.1.0")
```

后端每次修改 proto 后：

1. 执行 `buf generate`。
2. 生成 Kotlin / Java 协议代码。
3. 发布 Maven 包。
4. 更新客户端依赖版本。
5. 在变更说明中标记兼容性。

优点：

- 客户端独立编译。
- 协议版本可追踪。
- 不需要复制 `proto` 和 `gen`。
- 多台机器不会产生生成代码漂移。

### 7.2 最终方案：Buf Schema Registry

协议分发按一步到位设计，最终使用 Buf Schema Registry 或等价的内部协议发布机制：

- 后端发布 proto module。
- 客户端按 module version 拉取。
- CI 检查 breaking change。
- 自动生成多语言 SDK。

## 八、仓库拆分建议

### 8.1 Android 目录必须自包含

无论是否立即拆独立仓库，Android 目录都必须自包含：

```text
frontend/android
├── app
├── gradle
├── build.gradle.kts
├── settings.gradle.kts
├── README.md
├── local.properties.example
└── PROTO_VERSION
```

要求：

- 在 `frontend/android` 目录内执行 `./gradlew assembleDebug` 即可构建。
- 不引用 `../../backend`。
- 不引用 `../../gen`。
- 不要求 Docker Compose。

### 8.2 最终仓库边界

按长期目标，仓库边界设计为：

```text
antclaw-server
antclaw-android
antclaw-proto
```

职责：

| 仓库 | 职责 |
|---|---|
| `antclaw-server` | Go 后端、worker、部署、数据库迁移 |
| `antclaw-android` | Android 客户端、UI、移动端缓存、系统通知 |
| `antclaw-proto` | proto 定义、breaking check、SDK 发布 |

要求：

- 协议包可发布。
- `api.alfq.org` 是稳定 API 入口。
- Android CI 可独立构建。
- 版本兼容策略明确。

## 九、联调流程

### 9.1 后端开发机准备

后端机器执行：

```bash
docker compose -f deploy/docker-compose.yaml --project-name antclaw up -d --build api worker admin
```

确认：

```bash
curl -i https://api.alfq.org/antclaw.v1.SystemService/Healthz \
  -H 'Content-Type: application/json' \
  --data '{}'
```

跨物理机联调统一使用 `https://api.alfq.org/`。

### 9.2 Android 开发机准备

Android 机器只需要：

```text
JDK 17
Android Studio
Android SDK
Gradle wrapper
客户端仓库或 frontend/android 目录
```

配置：

```properties
BASE_URL=https://api.alfq.org/
```

构建：

```bash
./gradlew assembleDebug
```

### 9.3 联调检查清单

- 登录接口成功。
- Connect-RPC 请求带 `Authorization`。
- 401 后能退出或刷新登录。
- `/sse/notifications` 能连接。
- 后端 Redis Pub/Sub 推送后 Android 能收到。
- App 后台再前台后能补拉未读。
- Debug 页面显示当前 API Base URL。

## 十、CI/CD 改造

### 10.1 后端 CI

后端 CI 必须：

- `go vet ./...`
- `go test ./...`
- `buf lint`
- `buf breaking`
- `buf generate`
- 发布 proto Android 包或生成 proto artifact。
- 部署 staging API。

### 10.2 Android CI

Android CI 必须：

- 拉取指定 proto Android 包版本。
- `./gradlew assembleDebug`
- `./gradlew testDebugUnitTest`
- 检查 `BASE_URL` 不硬编码到非预期环境。
- Release 包只能使用 production 配置。

### 10.3 契约测试

新增契约测试：

- Android 使用的 proto 版本必须兼容当前 staging 后端。
- staging 后端必须提供 `SystemService/Healthz`。
- `NotificationService/UnreadCount` 必须可用。
- `/sse/notifications` 未登录返回 401，登录后返回 `text/event-stream`。

## 十一、安全要求

- 客户端不得保存后端数据库地址、Redis 地址、内部 Docker 域名。
- 客户端不得内置管理员 token。
- Debug 环境 token 与 production token 隔离。
- 外网联调必须使用 HTTPS。
- 如允许 HTTP，仅限 Debug 和局域网环境，并通过 Android network security config 明确限制。
- Release 包禁止连接 `http://`。

## 十二、实施里程碑

### 阶段一：配置解耦

- Android `BASE_URL` 改为 flavor / Gradle property。
- 新增 `local.properties.example`。
- Debug 页面显示当前环境。
- 文档说明模拟器与真机地址区别。

### 阶段二：协议解耦

- 明确 Android proto 来源。
- 优先发布内部 Maven 协议包。
- 若暂不具备 Maven，增加 `PROTO_VERSION` 与同步脚本。
- 禁止 Android 依赖后端本地路径。

### 阶段三：远程联调环境

- 确认 `https://api.alfq.org/` 可访问。
- 确认 Cloudflare Tunnel 到 `localhost:8082` 正常。
- 确认 Connect-RPC 与 SSE 代理配置。
- 提供测试账号和测试数据。

### 阶段四：Android 通知链路

- 实现 SSE 客户端。
- 前台连接、后台断开、前台补拉未读。
- 401 处理。
- 系统通知渠道。

### 阶段五：CI 与契约测试

- 后端发布协议包。
- Android CI 独立构建。
- staging 契约测试。
- 版本兼容策略落地。

## 十三、验收标准

- Android 目录可在另一台物理机独立打开并构建。
- Android 构建不依赖 `/opt/antclaw/backend`、`/opt/antclaw/gen`。
- Android 默认 `BASE_URL` 为 `https://api.alfq.org/`。
- 真机能访问远程后端并登录成功。
- Connect-RPC 调用成功。
- `/sse/notifications` 登录后能建立连接。
- 后端推送通知后 Android 能收到并更新未读数。
- 后端 proto 变更后有明确版本同步流程。
- Release 包不会误连 `ad.alfq.org`、`localhost` 或 `:8082`。

## 十四、最终推荐

按一步到位方案执行：

1. `api.alfq.org` 作为 Android 唯一 API 根域名。
2. Cloudflare Tunnel 将 `api.alfq.org` 转发到 `http://localhost:8082`。
3. Android `BASE_URL` 固定为 `https://api.alfq.org/`。
4. Android 不访问 `ad.alfq.org`，不直连 `8082`。
5. proto 生成代码发布为 Android 可依赖的版本化包。
6. Android 实现独立 SSE 客户端和前台补拉机制。
7. 后端与 Android 分别建立 CI，并增加契约测试。
8. 条件成熟后拆分为独立 Android 仓库。

按该设计，Android 客户端可以在另一台物理机上只依赖 `https://api.alfq.org/` 完成开发、构建和联调。
