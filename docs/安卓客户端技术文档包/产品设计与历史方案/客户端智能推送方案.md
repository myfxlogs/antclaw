# 客户端智能推送方案

## 归档状态

- **状态**：已完成归档
- **归档原因**：本方案对应的代码实施已完成，后续仅作为历史设计依据和回归验收参考。新开发不得把本文未完成事项当作当前待办，需以实施完成报告和现行技术文档包为准。
- **后续使用**：只读参考；如与上级技术文档包冲突，以上级技术文档包为准。

## 一、目标

参考 `emulator/ark-intelligent` 的推送频率与消息类型，在 AntClaw 当前架构上实现面向客户端的智能推送能力。

目标不是新增一套独立通知系统，而是复用现有链路：

```text
worker 业务检测
  → internal/notify.Service.Send
  → notifications 表持久化
  → Redis Pub/Sub user:{user_id}:notifications
  → /sse/notifications
  → Android 客户端通知中心 / Snackbar / Badge / 系统通知
```

核心要求：

- 与 `ark-intelligent` 保持同等消息类型。
- 与 `ark-intelligent` 保持同等检查频率。
- 不伪造数据；数据不足时不发送结论型推送。
- 所有推送必须可追溯、可去重、可按用户偏好过滤。
- 离线用户重新打开客户端后仍可从通知历史看到未读消息。

## 二、当前项目已有基础

AntClaw 已具备以下能力：

| 能力 | 当前实现 |
|---|---|
| 通知中枢 | `backend/internal/notify/notify.go` |
| 通知落库 | `notifications` 表 |
| 用户通知偏好 | `user_notification_prefs` |
| 通知 RPC | `NotificationService`，支持未读、历史、已读、偏好配置 |
| 实时推送 | `/sse/notifications` |
| 实时通道 | Redis Pub/Sub：`user:{uuid}:notifications` |
| worker 调度 | `backend/cmd/antclaw-worker/main.go` |
| 用户策略告警 | `alert_evaluator.go` |
| 告警过滤 | `internal/service/alerts/gate.go` |

因此本方案主要新增：

- 推送事件检测器。
- 推送调度频率。
- 推送消息类型规范。
- 去重键与冷却规则。
- Android 客户端呈现策略。

## 三、本次改造范围

本次落地必须同时修改后端和 Android 客户端，不能只做其中一端。

### 3.1 后端必须修改

后端负责“是否应该推、推给谁、推什么、是否重复”的全部业务判断。

必须新增或改造：

| 模块 | 必须修改内容 |
|---|---|
| `backend/cmd/antclaw-worker` | 新增推送调度循环，按 1m / 30m / 1h / 4h / 6h / weekly 频率执行检测 |
| `backend/internal/notify` | 继续作为唯一通知出口；必要时补充便捷 builder，但不能绕过 `notify.Service.Send` |
| PostgreSQL migration | 新增 `notification_push_state`、`user_alert_preferences` |
| sqlc 查询 | 增加 push state upsert、业务偏好读取、批量用户扫描 |
| `NotificationService` | 如当前 proto 不足以配置业务偏好，需要新增偏好 RPC |
| worker 检测器 | 实现 calendar、actual、surprise、digest、macro、COT、regime、options、onchain 推送检测 |
| 测试 | 增加推送去重、静默期、偏好过滤、跨重启不重复发送测试 |

后端不负责客户端样式，也不直接关心 Android UI 展示细节。后端只输出结构化通知字段：

```text
category  = alert | signal | digest | system
severity  = low | normal | high | critical
title     = 简短标题
body      = 正文摘要
data      = 可跳转上下文，例如 event_id / symbol / route / source
dedup_key = 业务幂等键
```

### 3.2 Android 客户端必须修改

Android 客户端位于：

```text
frontend/android
```

当前客户端是 Kotlin + Jetpack Compose + Material3，主题入口为：

```text
frontend/android/app/src/main/java/com/antclaw/alfq/ui/theme/Theme.kt
```

当前客户端已有 `AlfQTheme`、底部导航、登录态、Feed、AlertScreen 等基础页面，但仍需要实现完整通知体验：

| 模块 | 必须修改内容 |
|---|---|
| 主题色 | 将当前蓝色主色调整为 `/opt/antclaw/emulator/anttrader` 前端的金色/深石墨色系 |
| 网络层 | 接入 `/sse/notifications` 或 Android 可稳定运行的等效长连接方案 |
| 通知仓库 | 拉取 `NotificationService/ListUnread`、`UnreadCount`、`MarkAsRead`、`MarkAllRead`、`GetPrefs`、`UpdatePrefs` |
| UI 状态 | 保存未读数、通知列表、SSE 连接状态、错误状态 |
| 通知中心 | 新增或完善通知列表页，支持 category/severity 分组与已读 |
| 即时提示 | `alert` / `signal` 使用 Snackbar 或 App 内横幅提示；`digest` 默认只进通知中心 |
| Badge | 底部“消息”入口显示真实未读数，替换当前硬编码 `notificationCount = 3` |
| 系统通知 | App 在后台时，高优先级通知应进入 Android 系统通知栏 |
| 偏好设置 | 新增业务推送偏好设置页，对应 `user_alert_preferences` |

### 3.3 不需要修改 Web 前端

本项目当前客户端目标是 Android，不以 `frontend/admin` Web 管理端为主要落地点。

Web 管理端可以后续增加推送监控、用户偏好管理、通知审计等管理能力，但不属于本阶段客户端推送体验的主路径。

## 四、消息类型与频率矩阵

### 4.1 高频经济日历推送

| 消息类型 | 检查频率 | 实际推送时机 | AntClaw 数据来源 | 通知分类 |
|---|---:|---|---|---|
| 事件前提醒 | 每 1 分钟 | 事件前用户设定的 X 分钟，例如 5/15/30/60/120 分钟 | `calendar_events` | `alert` |
| 数据公布提醒 | 每 1 分钟探测 | actual 首次出现时立即推送 | `calendar_events.actual` / MQL5 actuals | `alert` |
| Surprise / Confluence 更新 | actual 首次出现后立即计算 | surprise 达到阈值时推送 | `calendar_surprise_history`、`event_impact_records`、`cot_analyses` | `signal` |
| 事件后补采 | 事件后 1/3/5/10/15/20/30 分钟 | 只采集和触发 actual 检测，不一定每次推送 | MQL5 actuals | 内部任务 |

设计说明：

- worker 每分钟扫描当天未来 120 分钟内的经济日历事件。
- 用户偏好决定提醒提前量、影响级别、货币范围。
- 同一用户、同一事件、同一提前分钟数只推送一次。
- actual 首次从空变为非空时触发公布提醒。
- surprise 分数绝对值不足阈值时只落库，不实时推送。

建议阈值：

| 严重度 | 条件 |
|---|---|
| `high` | high impact 事件 actual 发布 |
| `critical` | high impact 且 `abs(surprise_score) >= 2.0` |
| `normal` | medium impact 事件 actual 发布 |

### 4.2 每日固定推送

| 消息类型 | 检查频率 | 实际推送时机 | 通知分类 |
|---|---:|---|---|
| 每日 News Radar 晨报 | 每 1 分钟检查 | 每天 06:00，用户本地时区 | `digest` |
| 每日综合 Briefing | 每 30 分钟检查 | 每天 06:00，用户本地时区，每天最多一次 | `digest` |

晨报内容：

- 当日 high / medium / low 事件数量。
- 用户订阅货币对应的首个重要事件。
- Storm Day 提醒：当日 high impact 事件数量大于等于 3。
- 可能受影响的交易品种，例如 EURUSD、GBPUSD、USDJPY、DXY。

综合 Briefing 内容：

- 今日宏观事件。
- 最新 COT 偏向。
- 主要 regime 状态。
- 重点期权风险，例如 GEX / IV skew 异常。
- 用户关注品种的关键价位或信号变化。

### 4.3 每小时检查，有变化才推送

| 消息类型 | 检查频率 | 实际推送条件 | 通知分类 |
|---|---:|---|---|
| 宏观 regime 变化 | 每 1 小时 | `macro_regime_history` 或派生 regime 发生变化 | `alert` |
| FRED / 宏观关键指标异动 | 每 1 小时 | 指标跨阈值、方向反转、状态变化 | `alert` |
| 期权风险状态变化 | 每 1 小时 | GEX、IV skew、DVOL、VIX term structure 状态变化 | `alert` |
| 链上 / DeFi 风险变化 | 每 1 小时 | TVL、netflow、MVRV、SOPR 状态变化 | `alert` |

去重规则：

- 同一用户、同一指标、同一状态，10 分钟内只推送一次。
- 同一 alert type 1 小时内最多 3 次，沿用 `alerts.Gate` 设计。

### 4.4 每 4 小时检查，有变化才推送

| 消息类型 | 检查频率 | 实际推送条件 | 通知分类 |
|---|---:|---|---|
| Carry Trade Unwind 风险 | 每 4 小时 | carry 排名、利差方向、避险状态发生显著变化 | `alert` |
| Regime Transition | 每 4 小时 | `regime_transitions` 新增状态迁移 | `alert` |
| 多资产风险共振 | 每 4 小时 | 宏观、期权、情绪、价格至少 2 类同时触发风险条件 | `signal` |

### 4.5 每 6 小时检查，低频触发

| 消息类型 | 检查频率 | 实际推送条件 | 通知分类 |
|---|---:|---|---|
| COT 新数据发布 | 每 6 小时 | COT report date 大于上次推送日期 | `alert` |
| COT 强信号 | 每 6 小时 | 新信号强度达到阈值 | `signal` |
| Walk-forward / calibration 质量变化 | 每 6 小时 | 胜率、校准、回测质量明显变化 | `digest` |

COT 实际发布频率约每周一次，因此虽然每 6 小时检查，正常只会每周推送一次新数据通知。

### 4.6 每周固定推送

| 消息类型 | 检查频率 | 实际推送时机 | 通知分类 |
|---|---:|---|---|
| Weekly Macro Outlook | 每 1 小时检查 | 每周日 18:00 WIB 或配置时区对应时间 | `digest` |
| 周度 COT / Regime 总结 | 每 1 小时检查 | 每周日固定窗口，每周最多一次 | `digest` |

## 五、推荐新增后端模块

### 5.1 Worker 推送调度器

建议新增目录：

```text
backend/cmd/antclaw-worker/push_scheduler.go
backend/cmd/antclaw-worker/push_calendar.go
backend/cmd/antclaw-worker/push_macro.go
backend/cmd/antclaw-worker/push_cot.go
backend/cmd/antclaw-worker/push_digest.go
```

职责划分：

| 文件 | 职责 |
|---|---|
| `push_scheduler.go` | 创建 1m / 30m / 1h / 4h / 6h ticker，统一调度 |
| `push_calendar.go` | 事件前提醒、actual 发布提醒、surprise 推送 |
| `push_macro.go` | 宏观 regime、FRED、carry、期权/链上风险推送 |
| `push_cot.go` | COT 新发布、强信号、校准状态推送 |
| `push_digest.go` | 晨报、综合 briefing、周报 |

要求：

- 所有 I/O 函数第一个参数为 `ctx context.Context`。
- 所有推送统一调用 `notify.Service.Send`。
- 禁止 handler 直连数据库做推送检测。
- 所有检测器只依赖 PostgreSQL、Redis 与已落库数据，不直接伪造行情或宏观数据。

### 5.2 推送状态表

为保证重启后不重复发送，需要增加推送状态表。

建议迁移：

```text
backend/internal/adapter/storage/postgres/migrations/0xx_create_push_state.sql
```

建议表结构：

```sql
CREATE TABLE IF NOT EXISTS notification_push_state (
    id BIGSERIAL PRIMARY KEY,
    user_id UUID NOT NULL,
    event_key TEXT NOT NULL,
    push_type TEXT NOT NULL,
    last_sent_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    payload_hash TEXT NOT NULL DEFAULT '',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (user_id, event_key, push_type)
);

CREATE INDEX IF NOT EXISTS idx_notification_push_state_user_time
    ON notification_push_state(user_id, last_sent_at DESC);
```

`event_key` 示例：

| 场景 | event_key |
|---|---|
| 事件前提醒 | `calendar:{event_id}:pre:{minutes}` |
| actual 发布 | `calendar:{event_id}:actual` |
| surprise | `calendar:{event_id}:surprise:{bucket}` |
| 晨报 | `digest:daily:{user_id}:{yyyy-mm-dd}` |
| COT 发布 | `cot:release:{report_date}` |
| regime 变化 | `regime:{symbol}:{from}:{to}:{date}` |
| weekly outlook | `digest:weekly:{iso_year_week}` |

Redis `DedupKey` 只能处理短期重复；数据库状态表负责跨重启去重。

## 六、Worker 调度设计

在 `runCollectionLoop` 外新增独立推送循环，避免采集任务和推送任务相互阻塞。

推荐逻辑：

```text
runPushLoop
  ├── every 1m   → calendar pre-event / actual / surprise
  ├── every 30m  → daily briefing check
  ├── every 1h   → macro / options / onchain state changes / weekly outlook window
  ├── every 4h   → carry / regime transition / risk confluence
  └── every 6h   → COT release / strong COT signal / calibration summary
```

推送任务必须：

- 每次执行设置超时，例如 2 分钟。
- 单个用户发送失败不影响其他用户。
- 每次批量发送之间保留小延迟，避免 SSE/数据库瞬时压力。
- 对全站 digest 使用分页扫描用户，避免一次性加载过多用户。

## 八、Android 客户端接入方案

Android 客户端必须接入当前后端个人通知入口：

```text
/sse/notifications
```

### 8.1 通知链路

客户端启动后的推荐链路：

```text
用户登录成功
  → 保存 access token
  → 调用 NotificationService/UnreadCount
  → 调用 NotificationService/ListUnread
  → 建立 /sse/notifications 长连接
  → 收到 event: notification
  → 更新本地通知状态与 Badge
  → 按 category/severity 决定 Snackbar、横幅或系统通知
```

### 8.2 Android 网络实现要求

Android 端不能使用 Web 的 `EventSource`。必须按 Android 技术栈实现：

| 能力 | 推荐实现 |
|---|---|
| Connect RPC | 继续使用当前 Android Connect/gRPC-web 客户端封装 |
| SSE 长连接 | 使用 OkHttp `newCall(request).execute()` 读取 `text/event-stream`，或使用项目已有长连接封装 |
| 鉴权 | `Authorization: Bearer <access_token>` |
| 自动重连 | 指数退避，建议 1s → 2s → 5s → 15s → 30s，上限 30s |
| 401 处理 | 立即断开并引导重新登录，不允许无限重连 |
| App 后台 | 允许断开 SSE；恢复前台后先拉未读列表再重连 |
| 心跳 | 忽略 `: ping` 注释行，仅处理 `event: notification` 和后续 `data:` |

### 8.3 客户端状态模型

建议新增 Android 数据模型：

data class ClientNotification(

### 8.4 客户端行为

- 登录后建立 SSE 连接。
- 收到 `event: notification` 后：
  - 更新未读数。
  - 写入通知列表缓存。
  - `severity=high|critical` 弹 Snackbar 或 App 内横幅。
  - App 在后台且 `severity=high|critical` 时发 Android 系统通知。
  - `category=digest` 仅进入通知中心，不强弹，避免打扰。
- SSE 断开后自动重连。
- 401 时引导重新登录，不无限重连。

通知展示建议：

| category | 展示方式 |
|---|---|
| `alert` | Snackbar / 横幅 + 通知中心 + Badge |
| `signal` | Snackbar / 横幅 + 通知中心 + 可跳转图表 |
| `digest` | 通知中心 + Badge，不默认 Toast |
| `system` | 仅通知中心，critical 除外 |

### 8.7 Android 系统通知要求

App 后台时应使用 Android 系统通知承接高优先级推送。

最低要求：

- 创建通知渠道：`market_alerts`、`signals`、`digests`、`system`。
- `critical` 使用高优先级 channel，可震动。
- `digest` 使用低优先级 channel，不震动。
- 点击系统通知后跳转到对应页面：
  - `calendar_pre_event` → 日历/事件详情。
  - `calendar_actual` → 事件详情。
  - `signal` → 信号详情。
  - `regime` → 对应品种详情或 regime 页面。
  - `digest` → 通知中心或今日摘要页。

## 十二、风险与注意事项

| 风险 | 处理 |
|---|---|
| 经济日历时间为零值 | 不推送事件前提醒，只记录 warn |
| 上游 actual 延迟 | 事件后 1/3/5/10/15/20/30 分钟重复探测 |
| 用户量增长导致批量推送慢 | 分页扫描用户，批次间 sleep，后续可改队列 |
| SSE 断线漏实时消息 | 通知已落库，Android 恢复前台后调用未读列表补齐 |
| 过度打扰用户 | digest 默认不 Toast，alert 受静默期和 daily cap 限制 |
| 外部 API 失败 | 不发送伪结论，保留采集失败日志 |
| Android 后台长连接不稳定 | 后台可断开 SSE，依赖前台补拉未读；high/critical 可结合系统通知 |
| 色调迁移不彻底 | 以 `Theme.kt` 为唯一色彩入口，禁止页面硬编码旧蓝色 |

## 十三、最终推荐

优先实现顺序：

1. `notification_push_state` 跨重启去重。
2. 经济日历事件前提醒与 actual 发布提醒。
3. 每日 06:00 晨报。
4. COT 新数据发布与强信号提醒。
5. Regime / macro / options / onchain 状态变化提醒。
6. Android 通知中心、SSE 长连接、真实未读 Badge。
7. Android 业务偏好设置页。
8. Android 主题色迁移到 anttrader 金色/深石墨色系。

这样可以最快让客户端获得和 `ark-intelligent` 等价的核心推送体验，同时复用 AntClaw 已有通知系统，避免重复建设。
