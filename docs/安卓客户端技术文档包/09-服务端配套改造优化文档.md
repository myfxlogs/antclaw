# 服务端配套改造优化文档

## 一、结论

Android 客户端文档已明确以 `https://api.alfq.org/` 作为唯一 API 入口。服务端当前已经具备大部分基础能力：

- Connect-RPC 服务已集中注册在 `backend/cmd/antclaw-api/main.go`。
- 个人通知 SSE 已存在 `/sse/notifications`。
- SSE 鉴权已支持 `Authorization: Bearer <token>`。
- 后端内部监听 `:8080`，可通过 Docker 宿主机端口与 Cloudflare Tunnel 暴露。

但是，为了让 Android 客户端 AI Agent 能稳定落地，服务端仍建议做配套改造与治理。本文面向服务端 AI Agent，负责后端代码环境中的接口、分层、鉴权、分页、SSE、测试和部署校验；Android 客户端 Agent 只阅读 `10-X-Threads社交客户端落地指导.md`，不得在客户端环境直接修改服务端代码。

## 二、必须处理的问题

### 2.1 Android 当前代码域名与文档不一致

当前 Android 代码中存在：

```text
frontend/android/app/build.gradle.kts
```

实际配置为：

```kotlin
buildConfigField("String", "BASE_URL", "\"https://app.alfq.org/\"")
```

但客户端文档统一要求：

```text
https://api.alfq.org/
```

处理要求：

- Android 客户端必须改为 `https://api.alfq.org/`。
- 服务端文档、联调脚本、冒烟测试必须统一使用 `https://api.alfq.org/`。
- `app.alfq.org` 不再作为 Android API 域名，避免与 Web/App 展示域混淆。

### 2.2 `api.alfq.org` 暴露全量 RPC，需要明确管理接口安全边界

当前 API 入口注册了客户端接口和管理端接口，例如：

- `AdminService`
- `AdminDataService`
- `DataSourceService`
- `SystemAIService`

这些接口可以存在于同一个 API 进程，但必须满足：

- 未登录请求必须返回 `401`。
- 非管理员请求必须返回 `403`。
- 管理接口不得因公开域名暴露而绕过权限。
- Android 客户端文档禁止实现管理端接口，但服务端仍必须做强校验，不能只依赖客户端自律。

### 2.3 协议版本和客户端兼容性缺少服务端可查询入口

Android 独立开发需要知道当前服务端兼容的协议版本。现有 `SystemService/Info` 可作为基础，但建议明确返回：

- API 版本。
- proto 版本。
- build commit。
- server time。
- Android 最低兼容客户端版本。
- 是否维护模式。

如果已有字段不足，应扩展 `SystemService/Info` 或新增专门字段。

### 2.4 SSE 长连接需要更明确的生产级行为

`/sse/notifications` 已可用，但服务端需要保证：

- 未授权返回 `401`。
- 已授权连接立即返回可识别的连接事件或心跳。
- 心跳间隔稳定。
- 断开时释放 Redis 订阅。
- 日志记录 userID、连接建立、断开、错误原因。
- 不把敏感 token 写入日志。

### 2.5 缺少面向 `api.alfq.org` 的服务端冒烟测试

当前客户端文档依赖公共域名。如果没有自动化检查，Cloudflare Tunnel、路由、SSE、CORS/Headers、认证很容易漂移。

必须增加或完善脚本：

```text
scripts/smoke-api-domain.sh
```

覆盖：

- `SystemService/Healthz`。
- `SystemService/Info`。
- 未登录访问 `/sse/notifications` 返回 `401`。
- 登录接口可达。
- 使用 token 访问 `NotificationService/UnreadCount`。
- 非管理员访问管理端接口返回 `403` 或 `401`。

### 2.6 X / Threads 社交接口仍偏原型实现

Android 社交客户端需要稳定的 Feed / Profile / Follow / Like / Comment / Share 后端能力。当前 `FeedService` / `TraderService` 已有基础 proto 和数据库表，但服务端实现仍存在以下问题：

- `backend/internal/adapter/rpc/alfq_feed_handler.go` 直接访问 DB，未走 `Handler -> Service -> Repository`。
- `backend/internal/adapter/rpc/alfq_trader_handler.go` 直接访问 DB，未走 `Handler -> Service -> Repository`。
- 多处 `QueryRow` / `Query` / `Exec` / `Scan` 错误被忽略。
- 部分社交 RPC 对空 `user_id`、未登录、越权、帖子不存在、用户不存在处理不足。
- `GetFeed` 使用 `id > cursor`，但排序是 `created_at DESC`，游标与排序不一致。
- `GetFeedRequest.filter` 字段未真实影响结果。
- `GetPost` 返回字段与 `GetFeed` 列表字段不一致。
- `SharePost` 只创建 `post_type='share'` 文本，没有保留原帖引用关系。
- `TraderService` 未完整处理自关注、重复关注、分页游标、`bio`、交易指标和用户不存在。

## 四、社交接口后端补齐规格

本章是给后端 AI Agent 的可执行规格。实现时必须先改 proto，再执行 `buf generate`，再按 `Handler -> Service -> Repository` 分层落地。禁止为了让 Android 页面“看起来可用”而返回合成数据。

### 4.1 P0 必须新增 / 修复的 Feed proto

当前 `FeedService` 缺少帖子评论列表、个人主页内容列表、回复关系、稳定引用关系。建议先在 `proto/antclaw/v1/alfq_feed.proto` 扩展：

```proto
service FeedService {
  rpc CreatePost(CreatePostRequest) returns (Post);
  rpc GetFeed(GetFeedRequest) returns (FeedResponse);
  rpc GetPost(GetPostRequest) returns (Post);
  rpc LikePost(LikePostRequest) returns (Post);

  rpc CommentOnPost(CommentRequest) returns (Comment);
  rpc ListComments(ListCommentsRequest) returns (ListCommentsResponse);
  rpc SharePost(SharePostRequest) returns (Post);
```

```proto
message Post {
```

### 4.2 P0 数据库 migration 要求

实现前先检查现有表结构。若字段不存在，新增 migration：

```sql
ALTER TABLE alfq_comments
  ADD COLUMN IF NOT EXISTS parent_comment_id uuid NULL REFERENCES alfq_comments(id);

ALTER TABLE alfq_posts
  ADD COLUMN IF NOT EXISTS original_post_id uuid NULL REFERENCES alfq_posts(id);

CREATE INDEX IF NOT EXISTS idx_alfq_posts_feed_cursor
  ON alfq_posts (created_at DESC, id DESC);

CREATE INDEX IF NOT EXISTS idx_alfq_posts_author_cursor
  ON alfq_posts (author_id, created_at DESC, id DESC);

CREATE INDEX IF NOT EXISTS idx_alfq_posts_type_cursor
  ON alfq_posts (post_type, created_at DESC, id DESC);

CREATE INDEX IF NOT EXISTS idx_alfq_comments_post_cursor
  ON alfq_comments (post_id, created_at ASC, id ASC);

CREATE INDEX IF NOT EXISTS idx_alfq_comments_parent
  ON alfq_comments (parent_comment_id);
```

如果现有 migration 系统已使用 goose / sqlc / 自定义脚本，必须按项目现有方式新增，不得临时在 Handler 中建表。

### 4.3 Feed 稳定游标规范

`GetFeed` 当前用 `id > cursor` 但排序是 `created_at DESC`，必须改为稳定复合游标。

游标格式：

```text
base64url(json({"created_at":"RFC3339Nano","id":"uuid"}))
```

服务端行为：

- `cursor == ""`：取第一页。
- `cursor` 非空但无法解析：返回 `InvalidArgument`。
- 排序统一：`ORDER BY created_at DESC, id DESC`。
- 下一页条件：`(created_at, id) < ($cursor_created_at, $cursor_id)`。
- `page_size <= 0` 使用 20。
- `page_size > 50` 截断为 50。

SQL 形态：

```sql
SELECT ...
FROM alfq_posts p
WHERE p.visibility = 'public'
  AND (
    $filter = 'all'
    OR ($filter = 'signals_only' AND p.post_type = 'signal_card')
    OR ($filter = 'posts_only' AND p.post_type = 'text')
    OR ($filter = 'shares' AND p.post_type = 'share')
  )
  AND (
    $cursor_empty
    OR (p.created_at, p.id) < ($cursor_created_at, $cursor_id)
  )
ORDER BY p.created_at DESC, p.id DESC
LIMIT $limit;
```

`ListUserPosts` 使用同样 cursor，但额外增加：

```sql
AND p.author_id = $user_id
```

### 4.4 Feed 返回字段统一规范

`GetFeed`、`GetPost`、`CreatePost`、`LikePost`、`UnlikePost`、`SharePost` 返回的 `Post` 必须使用同一个 Repository mapper，不允许各 RPC 自己拼字段。

每个返回的 `Post` 至少包含：

- `id`
- `author_id`
- `author_name`
- `content`
- `post_type`
- `signal_pair`
- `signal_direction`
- `signal_confidence`
- `visibility`
- `circle_id`
- `like_count`
- `comment_count`
- `share_count`
- `liked_by`
- `created_at`
- `original_post_id`

计数字段从真实表聚合：

```sql
(SELECT COUNT(*) FROM alfq_likes WHERE post_id = p.id) AS like_count
(SELECT COUNT(*) FROM alfq_comments WHERE post_id = p.id) AS comment_count
(SELECT COUNT(*) FROM alfq_posts WHERE original_post_id = p.id AND post_type = 'share') AS share_count
```

`liked_by` P0 可只返回当前用户是否点赞所需的数据：

- 若当前用户已登录且点赞，返回包含当前用户 ID 的数组。
- 未登录或未点赞返回空数组。

不要返回全量点赞用户列表，避免隐私和响应过大。

### 4.5 评论列表与回复树规范

P0 先实现扁平评论列表，P1 Android 可按 `parent_comment_id` 组装树。

`ListComments` 行为：

- 未登录可读 public 帖子的评论。
- 非 public 帖子必须做可见性判断。
- `post_id` 不存在返回 `NotFound`。
- `cursor` 使用 `created_at ASC, id ASC` 复合游标。
- `page_size <= 0` 使用 50。
- `page_size > 100` 截断为 100。

SQL 形态：

```sql
SELECT id, post_id, author_id, author_name, content, parent_comment_id, created_at
FROM alfq_comments
WHERE post_id = $post_id
  AND (
    $cursor_empty
    OR (created_at, id) > ($cursor_created_at, $cursor_id)
  )
ORDER BY created_at ASC, id ASC
LIMIT $limit;
```

`CommentOnPost` 行为：

- 未登录返回 `Unauthenticated`。
- `post_id` 不存在返回 `NotFound`。
- `parent_comment_id` 非空时必须属于同一 `post_id`，否则返回 `InvalidArgument`。
- 无权限评论返回 `PermissionDenied`。
- 成功后真实增加 `comment_count` 的聚合结果。

### 4.6 Share / Quote 语义规范

当前 `SharePost` 只创建 `post_type='share'` 文本，无法渲染引用卡片。必须补 `original_post_id`。

行为：

- `SharePost.post_id` 是被引用原帖。
- 原帖不存在返回 `NotFound`。
- 原帖不可见返回 `PermissionDenied`。
- 新帖：
  - `post_type = "share"`
  - `content = comment`
  - `original_post_id = req.post_id`
  - `visibility = "public"`，除非 proto 后续扩展支持 visibility。

P0 只返回 `original_post_id`。P1 如需完整引用卡片，可扩展：

```proto
Post original_post = 17;
```

但 P0 不建议递归返回，避免响应膨胀和循环引用。

### 4.7 可见性与鉴权规范

所有社交写操作必须要求登录：

- `CreatePost`
- `LikePost`
- `UnlikePost`
- `CommentOnPost`
- `SharePost`
- `Follow`
- `Unfollow`

未登录统一返回：

```text
connect.CodeUnauthenticated
```

可见性规则：

| visibility | 读取规则 |
|---|---|
| public | 任何用户可读 |
| followers | 作者本人或关注作者的人可读 |
| circle | 作者本人或圈子成员可读 |

P0 如果 `circle` 成员关系尚未实现：

- `CreatePost(visibility="circle")` 返回 `InvalidArgument`。
- 不要接受后再让所有人可见。

错误码规范：

| 场景 | Connect Code |
|---|---|
| 未登录写操作 | `Unauthenticated` |
| 参数格式错误 | `InvalidArgument` |
| 帖子 / 用户 / 评论不存在 | `NotFound` |
| 无权访问 | `PermissionDenied` |
| 重复点赞 / 重复关注 | 幂等成功 |
| 取消不存在点赞 / 关注 | 幂等成功 |
| DB 错误 | `Internal` |

### 4.8 Trader / Profile / Follow 补齐规范

`TraderService` P0 必须补齐：

- `GetProfile` 返回用户不存在时 `NotFound`。
- `Follow` 禁止自关注，返回 `InvalidArgument`。
- `Follow` 重复调用幂等成功，返回真实 `follower_count`。
- `Unfollow` 对未关注幂等成功，返回真实 `follower_count`。
- `GetFollowers` / `GetFollowing` 使用稳定 cursor，不再只 `LIMIT`。

建议扩展 `TraderProfile`：

```proto
bool is_following = 16;
```

如果不想改 `TraderProfile`，则新增：

```proto
rpc GetFollowState(GetFollowStateRequest) returns (GetFollowStateResponse);

message GetFollowStateRequest {
  string target_user_id = 1;
}

message GetFollowStateResponse {
  bool is_following = 1;
}
```

优先推荐直接扩展 `TraderProfile.is_following`，Android Profile 页可少一次请求。

### 4.9 P1 Search 接口规格

搜索属于 P1，不阻塞 P0 社交闭环。若开工，新增 `proto/antclaw/v1/search.proto`：

```proto
service SearchService {
  rpc Search(SearchRequest) returns (SearchResponse);
}

message SearchRequest {
  string query = 1;
  string cursor = 2;
  int32 page_size = 3;
  repeated string scopes = 4; // users / posts / symbols
}

message SearchResponse {
  repeated UserSearchResult users = 1;
  repeated Post posts = 2;
  repeated SymbolSearchResult symbols = 3;
  string next_cursor = 4;
}

message UserSearchResult {
  string user_id = 1;
  string display_name = 2;
  string tier = 3;
  int32 follower_count = 4;
}

message SymbolSearchResult {
  string symbol = 1;
  string display_name = 2;
  string market = 3;
}
```

P1 简化规则：

- `query` trim 后少于 2 个字符返回 `InvalidArgument`。
- `scopes` 为空时默认搜索 `users/posts/symbols`。
- 只返回当前用户有权限查看的 posts。
- 不返回合成 symbol；必须来自已有品种表或明确的数据源。

### 4.10 P1 Trends / Hot Symbols 接口规格

趋势功能属于 P1。新增 `proto/antclaw/v1/trend.proto`：

```proto
service TrendService {
  rpc ListTrendingTopics(ListTrendingTopicsRequest) returns (ListTrendingTopicsResponse);
  rpc ListHotSymbols(ListHotSymbolsRequest) returns (ListHotSymbolsResponse);
}

message ListTrendingTopicsRequest {
  string window = 1; // 1h / 24h / 7d
  int32 limit = 2;
}

message TrendingTopic {
  string topic = 1;
  int32 post_count = 2;
  int32 engagement_count = 3;
}

message ListTrendingTopicsResponse {
  repeated TrendingTopic topics = 1;
}

message ListHotSymbolsRequest {
  string window = 1; // 1h / 24h / 7d
  int32 limit = 2;
}

message HotSymbol {
  string symbol = 1;
  int32 post_count = 2;
  int32 signal_count = 3;
  int32 engagement_count = 4;
}

message ListHotSymbolsResponse {
  repeated HotSymbol symbols = 1;
}
```

统计窗口必须只允许：

```text
1h, 24h, 7d
```

算法 P1 默认：

```text
engagement_count = like_count + comment_count + share_count
```

如果后续要引入加权算法，必须另写文档，不得悄悄改变排序。

### 4.11 P2 推荐交易员接口规格

推荐交易员属于 P2。新增或扩展 `TraderService`：

```proto
rpc ListRecommendedTraders(ListRecommendedTradersRequest) returns (UserList);

message ListRecommendedTradersRequest {
  string cursor = 1;
  int32 page_size = 2;
}
```

P2 默认推荐规则需先确认。若用户未指定，后端 AI Agent 不得猜算法。可选方案：

1. 按 `follower_count DESC`。
2. 按认证等级 + 粉丝数。
3. 按交易表现认证指标。
4. 按近期发帖活跃度。

未确认前只允许写 proto 草案和 TODO 文档，不允许返回随机推荐。

## 八、AI Agent 实现要求

AI Agent 在执行服务端变更时必须遵守：

- Handler 不直接访问数据库，保持 `adapter/rpc → service → infra/postgres`。
- 新增或修改 proto 后必须执行 `buf generate`。
- 不手动编辑 `gen/`。
- 不返回合成数据。
- 管理接口权限必须在服务端强制校验，不能只依赖前端隐藏入口。
- SSE 不得在日志中打印 token。
- 社交服务必须先补接口和仓储边界，再允许 Android 客户端依赖其行为。
- `GetFeed`、关注列表等分页接口必须使用稳定游标，不能用与排序无关的字段做 cursor。
- 未定义的推荐算法、分页大小、可见性规则、引用关系字段必须先更新 proto 或向用户确认，不能猜测。
- 修改后必须执行质量检查。

## 十、是否需要立即改服务端代码

当前不需要为了“让 Android 能连上 API”而大改服务端，因为 Connect-RPC 和 `/sse/notifications` 已存在。

但如果目标是落地“交易员版 X / Threads”社交客户端，则服务端必须同步完成社交接口治理，否则客户端只能做到页面接入，无法保证分页、过滤、点赞、关注、引用和错误态的真实一致性。

需要尽快完成以下服务端治理变更：

1. 增加 `api.alfq.org` 冒烟测试。
2. 审计管理端接口权限。
3. 增强 `SystemService/Info` 的版本信息。
4. 明确 proto/SDK 发布流程。
5. 增强 SSE 日志与测试。
6. 重构 `FeedService` / `TraderService` 分层与错误处理。
7. 修复 Feed 稳定游标、过滤、详情字段、社交写操作鉴权。
8. 补齐社交接口服务端测试与 E2E。

这些变更会让 Android 客户端 AI Agent 在独立机器上开发时有稳定、可验证、可追踪的后端依据。
