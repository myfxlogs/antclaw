# 服务端配套改造优化文档

## 一、结论

Android 客户端文档已明确以 `https://api.alfq.org/` 作为唯一 API 入口。服务端当前已经具备大部分基础能力：

- Connect-RPC 服务已集中注册在 `backend/cmd/antclaw-api/main.go`。
- 个人通知 SSE 已存在 `/sse/notifications`。
- SSE 鉴权已支持 `Authorization: Bearer <token>`。
- 后端内部监听 `:8080`，可通过 Docker 宿主机端口与 Cloudflare Tunnel 暴露。

但是，为了让 Android 客户端 AI Agent 能稳定落地，服务端仍建议做配套改造与治理。本文面向服务端 AI Agent，负责后端代码环境中的接口、分层、鉴权、分页、SSE、测试和部署校验；Android 客户端 Agent 只阅读 `10-X-Threads社交客户端落地指导.md`，不得在客户端环境直接修改服务端代码。

## 二、必须处理的问题

### 2.1 Android 当前代码域名与文档不一致

当前 Android 代码中存在：

```text
frontend/android/app/build.gradle.kts
```

实际配置为：

```kotlin
buildConfigField("String", "BASE_URL", "\"https://app.alfq.org/\"")
```

但客户端文档统一要求：

```text
https://api.alfq.org/
```

处理要求：

- Android 客户端必须改为 `https://api.alfq.org/`。
- 服务端文档、联调脚本、冒烟测试必须统一使用 `https://api.alfq.org/`。
- `app.alfq.org` 不再作为 Android API 域名，避免与 Web/App 展示域混淆。

### 2.2 `api.alfq.org` 暴露全量 RPC，需要明确管理接口安全边界

当前 API 入口注册了客户端接口和管理端接口，例如：

- `AdminService`
- `AdminDataService`
- `DataSourceService`
- `SystemAIService`

这些接口可以存在于同一个 API 进程，但必须满足：

- 未登录请求必须返回 `401`。
- 非管理员请求必须返回 `403`。
- 管理接口不得因公开域名暴露而绕过权限。
- Android 客户端文档禁止实现管理端接口，但服务端仍必须做强校验，不能只依赖客户端自律。

### 2.3 协议版本和客户端兼容性缺少服务端可查询入口

Android 独立开发需要知道当前服务端兼容的协议版本。现有 `SystemService/Info` 可作为基础，但建议明确返回：

- API 版本。
- proto 版本。
- build commit。
- server time。
- Android 最低兼容客户端版本。
- 是否维护模式。

如果已有字段不足，应扩展 `SystemService/Info` 或新增专门字段。

### 2.4 SSE 长连接需要更明确的生产级行为

`/sse/notifications` 已可用，但服务端需要保证：

- 未授权返回 `401`。
- 已授权连接立即返回可识别的连接事件或心跳。
- 心跳间隔稳定。
- 断开时释放 Redis 订阅。
- 日志记录 userID、连接建立、断开、错误原因。
- 不把敏感 token 写入日志。

### 2.5 缺少面向 `api.alfq.org` 的服务端冒烟测试

当前客户端文档依赖公共域名。如果没有自动化检查，Cloudflare Tunnel、路由、SSE、CORS/Headers、认证很容易漂移。

必须增加或完善脚本：

```text
scripts/smoke-api-domain.sh
```

覆盖：

- `SystemService/Healthz`。
- `SystemService/Info`。
- 未登录访问 `/sse/notifications` 返回 `401`。
- 登录接口可达。
- 使用 token 访问 `NotificationService/UnreadCount`。
- 非管理员访问管理端接口返回 `403` 或 `401`。

### 2.6 X / Threads 社交接口仍偏原型实现

Android 社交客户端需要稳定的 Feed / Profile / Follow / Like / Comment / Share 后端能力。当前 `FeedService` / `TraderService` 已有基础 proto 和数据库表，但服务端实现仍存在以下问题：

- `backend/internal/adapter/rpc/alfq_feed_handler.go` 直接访问 DB，未走 `Handler -> Service -> Repository`。
- `backend/internal/adapter/rpc/alfq_trader_handler.go` 直接访问 DB，未走 `Handler -> Service -> Repository`。
- 多处 `QueryRow` / `Query` / `Exec` / `Scan` 错误被忽略。
- 部分社交 RPC 对空 `user_id`、未登录、越权、帖子不存在、用户不存在处理不足。
- `GetFeed` 使用 `id > cursor`，但排序是 `created_at DESC`，游标与排序不一致。
- `GetFeedRequest.filter` 字段未真实影响结果。
- `GetPost` 返回字段与 `GetFeed` 列表字段不一致。
- `SharePost` 只创建 `post_type='share'` 文本，没有保留原帖引用关系。
- `TraderService` 未完整处理自关注、重复关注、分页游标、`bio`、交易指标和用户不存在。

## 四、推荐实现顺序

```text
S-01 统一域名文档和脚本
  → S-02 增加公共域名冒烟测试
  → S-03 审计管理接口权限
  → S-04 验证 SSE Bearer 鉴权
  → S-05 增强 System Info 版本信息
  → S-06/S-07/S-08/S-09 修复社交服务端基础闭环
  → S-10/S-11/S-14 增强日志、通知和社交测试
```

## 五、AI Agent 实现要求

AI Agent 在执行服务端变更时必须遵守：

- Handler 不直接访问数据库，保持 `adapter/rpc → service → infra/postgres`。
- 新增或修改 proto 后必须执行 `buf generate`。
- 不手动编辑 `gen/`。
- 不返回合成数据。
- 管理接口权限必须在服务端强制校验，不能只依赖前端隐藏入口。
- SSE 不得在日志中打印 token。
- 社交服务必须先补接口和仓储边界，再允许 Android 客户端依赖其行为。
- `GetFeed`、关注列表等分页接口必须使用稳定游标，不能用与排序无关的字段做 cursor。
- 未定义的推荐算法、分页大小、可见性规则、引用关系字段必须先更新 proto 或向用户确认，不能猜测。
- 修改后必须执行质量检查。

## 六、建议验收命令

后端本地质量检查：

```bash
cd backend && go vet ./... && go test ./... && go build ./...
```

文件大小与协议检查：

```bash
bash scripts/lint-filesize.sh
bash backend/scripts/lint-protocol.sh
```

公共域名冒烟测试：

```bash

```

容器更新：

```bash
docker compose -f deploy/docker-compose.yaml --project-name antclaw up -d --build api worker admin
```

## 七、是否需要立即改服务端代码

当前不需要为了“让 Android 能连上 API”而大改服务端，因为 Connect-RPC 和 `/sse/notifications` 已存在。

但如果目标是落地“交易员版 X / Threads”社交客户端，则服务端必须同步完成社交接口治理，否则客户端只能做到页面接入，无法保证分页、过滤、点赞、关注、引用和错误态的真实一致性。

需要尽快完成以下服务端治理变更：

1. 增加 `api.alfq.org` 冒烟测试。
2. 审计管理端接口权限。
3. 增强 `SystemService/Info` 的版本信息。
4. 明确 proto/SDK 发布流程。
5. 增强 SSE 日志与测试。
6. 重构 `FeedService` / `TraderService` 分层与错误处理。
7. 修复 Feed 稳定游标、过滤、详情字段、社交写操作鉴权。
8. 补齐社交接口服务端测试与 E2E。

这些变更会让 Android 客户端 AI Agent 在独立机器上开发时有稳定、可验证、可追踪的后端依据。
