# AntClaw 项目设计缺陷与工程化审查报告

> 审查日期：2026-05-16  
> 审查范围：`backend/`、`frontend/admin`、`frontend/web`、`frontend/android`、`proto/`、`scripts/`、`.github/`、`docs/安卓客户端技术文档包/`  
> 审查重点：客户端用户体验、真实数据契约、分层边界、测试与 CI 工程化

---

## 一、总体结论

当前项目已经具备较完整的技术骨架：Connect-RPC、SSE、PostgreSQL、Redis、Android Compose、Web/Admin Vite、proto 生成链路、Docker Compose、基础 CI 均已存在。但系统仍存在明显的“原型代码残留”和“工程约束只写在文档里、没有完全落入代码和 CI”的问题。

最影响产品质量的缺陷集中在四类：

1. **真实数据契约不稳定**：后端部分服务仍会在外部数据失败或无数据时返回样例/合成数据，违反项目“禁止合成数据 fallback”的铁律。
2. **客户端体验不一致**：Android、Web、Admin 的 loading/error/empty/retry、乐观更新、会话过期、SSE 重连策略不统一，用户很容易看到空白、静默失败或旧数据。
3. **前端工程化约束不足**：页面拆分、类型安全、API 封装、轮询禁令、`any` 禁令、测试覆盖没有被 CI 强制执行。
4. **后端分层和生产就绪度不均衡**：部分模块已完成 Service/Repository 化，但仍有内存态用户服务、样例宏观/日历服务、入口组装过重、公共错误模型不足等问题。

建议优先做一次“质量收口迭代”，目标不是新增功能，而是把文档中的铁律变成可执行的代码结构、lint、测试和 CI gate。

## 二、P0 级问题：会直接损害用户信任

### 2.1 后端仍存在样例/合成数据 fallback

**现象**

- `backend/internal/service/macro/service.go` 内置宏观样例序列，并在 FRED 拉取失败后继续返回 fallback 数据。
- `backend/internal/service/calendar/service.go` 在 MQL5 日历拉取失败后返回 `getSampleEvents()`。
- `backend/internal/service/user/service.go` 使用内存 map 和 `demo@antclaw.io` 预置用户，`GetMe` 在空 userID 时默认回退到 `user-1`。

**证据**

- `backend/internal/service/macro/service.go:49-73` 初始化硬编码 GDP、UNRATE、CPI、FedWatch 样例。
- `backend/internal/service/macro/service.go:168-193` FRED 失败后记录日志并返回 fallback。
- `backend/internal/service/calendar/service.go:35-41` MQL5 失败后使用 sample events。
- `backend/internal/service/calendar/service.go:108-134` 返回固定 NFP/ECB 样例事件。
- `backend/internal/service/user/service.go:30-55` 预置 demo user 和 sample history。
- `backend/internal/service/user/service.go:61-64` `userID == ""` 时默认 `user-1`。

**影响**

金融数据产品最核心的是数据可信度。用户无法分辨结果是真实市场数据、陈旧样例，还是外部数据源故障后的降级值。这会直接污染信号、报告、回测和客户端展示。

**建议**

- 所有数据服务改为：无数据或上游失败时返回明确业务错误，例如 `ErrDataInsufficient` / `connect.CodeUnavailable` / `connect.CodeNotFound`。
- 如果确实需要演示模式，必须显式通过配置启用，并在响应中带 `data_quality=demo/stale/live` 或类似字段，默认生产禁用。
- 增加 CI 扫描：禁止生产路径出现 `fallback to sample data`、`generate*Data`、`demo@`、`sample events` 等模式。

### 2.2 Android 会话管理链路没有真正接入 App 根状态

**现象**

Android 已经有 `SessionViewModel` 和 `SessionExpiredNotifier`，但 `AlfQApp` 顶层登录态仍用：

```kotlin
val isLoggedIn = remember { mutableStateOf(ConnectTransportProvider.getToken() != null) }
```

登录成功时只设置 token 和本地布尔值，没有使用 `SessionViewModel.onLoginSuccess()`。这会导致：

- refresh 失败后的 `RequireLogin` 事件难以驱动根导航回登录页。
- SSE connect/disconnect 生命周期和登录态分散。
- `userId`、`refreshToken`、显示名等会话信息没有统一入口。

**证据**

- `frontend/android/app/src/main/java/com/antclaw/alfq/AlfQApp.kt:45-70`
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/session/SessionViewModel.kt:46-63`
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/session/SessionViewModel.kt:65-82`

**影响**

用户 token 过期、refresh 失败、后台恢复、SSE 断开时，App 可能继续停留在业务页，随后各页面各自报错或静默失败。对移动端来说，这是高频且高损伤的体验问题。

**建议**

- `AlfQApp` 顶层改由 `SessionViewModel.session` 驱动导航。
- 登录/注册成功必须调用 `SessionViewModel.onLoginSuccess()`，不要直接改 `ConnectTransportProvider`。
- `MainContent` 的前后台生命周期改调 `SessionViewModel.onForeground/onBackground`。
- 增加根导航测试：refresh 失败后必须清 token、断 SSE、回登录页。

### 2.3 Admin 与 Web 仍有轮询和静默失败

**现象**

项目规则禁止 `setInterval` 轮询，要求使用 SSE。但 Admin 页面仍有 15 秒 / 30 秒轮询；多个 catch 直接忽略错误。

**证据**

- `frontend/admin/src/pages/Dashboard.tsx:51-70` 每 15 秒 `setInterval(fetchData, 15000)`。
- `frontend/admin/src/pages/Devices.tsx:19-29` 每 30 秒轮询设备列表。
- `frontend/admin/src/pages/Dashboard.tsx:64` 外层错误 `catch { /* ignore */ }`。
- `frontend/admin/src/pages/Devices.tsx:25` 错误 `catch { /* ok */ }`。

**影响**

- 用户在服务端故障时只看到旧数据或空状态，没有明确失败原因。
- 轮询会增加服务端压力，也和项目规定的 SSE 实时通道方向冲突。
- 管理端作为运维工具，静默失败比普通用户端更危险，因为它掩盖系统异常。

**建议**

- 在线用户、推送统计、设备状态优先接入现有 SSE 或新增只读 SSE 事件流。
- 所有管理页统一接入 `AsyncState<T>` / `AsyncView`，错误必须显示并提供重试。
- CI 增加前端扫描：禁止 `setInterval(`，除非路径在白名单并附带注释说明。

## 三、P1 级问题：客户端体验不一致

### 3.1 发布体验仍缺少完整产品闭环

**现状**

`PostViewModel` 已经从“布尔状态 + 吞错”改为 `PostState`，这是正确方向。但 `PostScreen` 仍存在体验缺口：

- 发布成功后只清空输入并 2 秒重置，没有自动返回上一页，也没有把新帖插入 Feed 顶部。
- 错误态里的“重试”按钮只是 `reset()`，并不会重试上一次发布。
- `signalPair` 输入框只有在 `signalPair.isNotBlank()` 时才显示，用户没有入口主动关联信号。
- 发帖没有字数限制、草稿保留、敏感失败文案规范。

**证据**

- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/post/PostScreen.kt:28-36`
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/post/PostScreen.kt:96-105`
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/post/PostScreen.kt:131-137`

**建议**

- 发布成功：回到 Feed 并触发顶部插入，或显示“已发布，查看”。
- 失败：保留草稿，重试按钮重新提交上一次 payload。
- 增加“关联品种/信号”入口，而不是靠非空状态触发表单字段。
- 发帖体验按 `docs/安卓客户端技术文档包/10-X-Threads社交客户端落地指导.md` 的 5.2 收口。

### 3.2 Feed / Social 两套信息流 ViewModel 重复实现

**现象**

`FeedViewModel` 和 `SocialFeedViewModel` 都实现了加载、刷新、分页、点赞、分享、Snackbar、乐观更新与回滚，但状态字段和错误策略不完全一致。

**证据**

- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/feed/FeedViewModel.kt:59-93`
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/feed/FeedViewModel.kt:95-126`
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/social/SocialFeedViewModel.kt:32-69`
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/social/SocialFeedViewModel.kt:73-101`

**影响**

同类交互在不同 Tab 或页面下出现不同加载态、失败态、回滚逻辑。后续任何行为改造都要改两份，容易出现回归。

**建议**

- 提取 `FeedTimelineController` 或 `TimelineUseCase`，统一分页、refresh、append、乐观更新、失败回滚。
- `FeedScreen` 与 Social/Discover 只保留不同筛选和渲染策略。
- 单元测试覆盖：首屏失败、append 失败不清空已有数据、点赞失败回滚、分享失败回滚、重复点击防抖。

### 3.3 SSE 客户端实现分裂

**现象**

- Android 有 `SseManager`，支持 OkHttp SSE 和指数退避。
- Web 的 `useSse.ts` 用 `fetch()` 手写读取 SSE stream。
- Admin 的 `openNotificationsSSE()` 使用 `EventSource`，并把 token 放在 query param。

**证据**

- `frontend/android/app/src/main/java/com/antclaw/alfq/data/sse/SseManager.kt:31-37`
- `frontend/web/src/features/_shared/useSse.ts:23-74`
- `frontend/admin/src/lib/api.ts:755-779`

**影响**

三端重连、鉴权、错误处理、心跳处理、事件解析都不一致。Web 端还违反“前端 API 调用禁止 `fetch()`”的项目规则，虽然 SSE 场景可讨论例外，但当前没有形成明确豁免和统一实现。

**建议**

- 定义跨端 SSE 行为规范：鉴权方式、401 处理、心跳、退避、前台补拉、最大重试、事件 schema。
- Web/Admin 统一使用 `EventSource` 或统一封装，不在页面层解析 stream。
- token 传递优先使用 Authorization；如果浏览器 EventSource 只能 query token，必须明确短期 token/一次性 token 策略，避免长期 access token 出现在 URL。

### 3.4 Android 文案与国际化不完整

**现象**

部分 Android 页面仍直接写英文文本，和已有多语言资源体系不一致。

**证据**

- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/device/DeviceInfoScreen.kt:35` 使用 `"Device Information"`。
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/device/DeviceInfoScreen.kt:38` 使用 `"Refresh"`。
- `frontend/android/app/src/main/java/com/antclaw/alfq/ui/device/DeviceInfoScreen.kt:59` 使用 `"Data collection consent denied"`。

**影响**

客户端已经有 `values-zh`、`values-ja`、`values-th` 等资源目录，但页面绕过资源文件会造成多语言体验不完整，也增加后续审查成本。

**建议**

- 增加 Android lint 或脚本扫描：Compose `Text("...")`、`contentDescription = "..."` 需要进入 string resources。
- 对设备信息采集页做产品化改造：解释采集目的、列出数据项、提供撤回授权和隐私入口。

## 四、P1 级问题：前端工程化不足

### 4.1 Admin API 聚合文件过大且职责混杂

**现象**

`frontend/admin/src/lib/api.ts` 约 780 行，集中包含认证、用户、任务、审计、策略、系统 AI、数据源、设备、通知、SSE 等所有 API 和映射逻辑。

**证据**

- `frontend/admin/src/lib/api.ts:1-780`
- 当前 `scripts/lint-filesize.sh` 阈值为 800 行，因此该文件接近硬上限但已经明显超过单一职责边界。

**影响**

API 变更会造成单文件高频冲突；类型、映射、业务默认值、SSE 都混在一起，难以测试。更重要的是，它让“Admin 接口”和“通用客户端接口”的边界在代码层消失。

**建议**

- 按领域拆分：`authApi.ts`、`usersApi.ts`、`jobsApi.ts`、`notificationsApi.ts`、`devicesApi.ts`、`systemAiApi.ts`、`dataSourcesApi.ts`。
- 每个模块只暴露明确 DTO，不返回 snake_case / camelCase 混合对象。
- 通知 SSE 从 `api.ts` 移入 `features/_shared/sse.ts`。

### 4.2 TypeScript 类型安全不足，`any` 大量存在

**现象**

Admin/Web 中大量使用 `any`、`as any` 绕过 proto 生成类型，尤其是 `frontend/admin/src/lib/api.ts`。

**证据**

- `frontend/admin/src/lib/api.ts:140-166`
- `frontend/admin/src/lib/api.ts:257-265`
- `frontend/admin/src/lib/api.ts:319-327`
- `frontend/admin/src/lib/api.ts:447-523`
- `frontend/admin/src/lib/api.ts:670`

**影响**

proto 字段变更无法被 TypeScript 编译器捕获，容易在运行时表现为空白、数字格式错误或页面崩溃。

**建议**

- 对 proto response 建立 typed mapper，禁止页面直接消费 `any`。
- `tsconfig` 开启更严格检查：`noImplicitAny`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` 视情况分阶段启用。
- CI 中 `pnpm -r lint` 不能 `|| true`。

### 4.3 Admin 页面组件拆分不足

**现象**

多个 Admin 页面远超“页面组件薄层”的工程规范：

- `SystemAI.tsx` 约 419 行。
- `Users.tsx` 约 307 行。
- `Jobs.tsx` 约 265 行。
- `PushManagement.tsx` 约 252 行。
- `DataSummary.tsx` 约 231 行。
- `Dashboard.tsx` 约 193 行。
- `Devices.tsx` 约 129 行。

**影响**

页面内同时混合状态、副作用、表单、渲染、错误处理和业务映射。迭代时很难只改一个行为而不影响其他 UI 状态。

**建议**

- 按项目规范拆为 `Page.tsx`、`hooks.ts`、`view.tsx`、`model.ts`。
- Admin 同样引入统一 `AsyncState<T>`，避免每页手写 `loading/error`。
- 对高风险操作（删除设备、重置密码、封禁用户、发送推送）建立统一确认 Modal 和结果 Toast，不使用 `alert/confirm`。

### 4.4 CI 对前端质量不具备强约束

**现象**

`.github/workflows/ci.yml` 中前端 install 和 lint 都允许失败：

- `pnpm install --frozen-lockfile || true`
- `pnpm -r lint || true`

**证据**

- `.github/workflows/ci.yml:101-104`

**影响**

前端 lint 实际上不是 gate。任何 TypeScript/ESLint 问题都能进入主干，导致工程规范只能靠人工记忆。

**建议**

- 去掉 `|| true`。
- 增加 `pnpm -r build` gate。
- 如果 eslint 尚未配置完整，先以 `tsc --noEmit` 作为强 gate。
- Android 增加 `./gradlew testDebugUnitTest` 或至少 `./gradlew test`。

## 五、P1 级问题：后端工程化与边界

### 5.1 API 入口过重，组合根缺少模块化

**现象**

`backend/cmd/antclaw-api/main.go` 同时负责配置、数据库、迁移、Redis、密钥、凭据、所有 service 初始化、handler 注册、CORS、SSE、HTTP server 生命周期。

**证据**

- `backend/cmd/antclaw-api/main.go:64-132` 基础设施与服务初始化。
- `backend/cmd/antclaw-api/main.go:161-269` handler 构造和注册。
- `backend/cmd/antclaw-api/main.go:271-301` CORS、SSE、server 组装。

**影响**

新增服务时容易在 main 中继续堆积依赖。测试组合根、替换 fake、分环境配置都困难。

**建议**

- 提取 `internal/app/api` 或 `cmd/antclaw-api/bootstrap`：
  - `LoadConfig`
  - `InitInfra`
  - `InitServices`
  - `RegisterRPC`
  - `RegisterSSE`
- main 保持为启动和信号处理。

### 5.2 公共错误模型不足

**现象**

服务层大量返回普通 `fmt.Errorf`，客户端只能拿到非结构化 message。文档中要求区分 401/403/参数错误/网络错误/服务端错误，但后端业务错误没有形成统一 code/detail。

**影响**

客户端难以实现稳定 UX：哪些错误可重试、哪些需要登录、哪些是输入错误、哪些是数据不足，目前只能靠字符串或 Connect code 猜测。

**建议**

- 定义领域错误：`ErrDataInsufficient`、`ErrPermissionDenied`、`ErrInvalidArgument`、`ErrUpstreamUnavailable`。
- Handler 层统一转换为 Connect code 和可本地化 message key。
- 文档补充“错误码与客户端行为矩阵”。

### 5.3 测试覆盖与规范不一致

**现象**

AGENTS 规定每个 `service/*` 包至少 1 个 `_test.go`，但多个 service 包没有测试，例如：

`admin`、`ai`、`alerts`、`audit`、`calendar`、`cot`、`datasource`、`macro`、`notify`、`presence`、`price`、`regime`、`report`、`sentiment`、`strategy`、`systemai`、`ta`、`user`、`vol` 等。

Android 只有少量单元测试，Web/Admin 没有发现 `.test.ts(x)` / `.spec.ts(x)`。

**影响**

核心行为靠 smoke 和人工检查兜底，无法防住局部回归。客户端高频交互如发帖、关注、通知权限、会话过期、SSE 断线恢复都缺少测试保护。

**建议**

- 后端先补 P0 包测试：`auth`、`feed`、`trader`、`notify`、`calendar`、`macro`、`user`。
- Android 先补 `PostViewModel`、`SessionViewModel`、`NotificationViewModel`、`MTAccountsViewModel`。
- Admin/Web 至少引入 Vitest + Testing Library，覆盖 API mapper 和关键 hooks。

## 六、P2 级问题：产品与体验细节

### 6.1 底部导航命名与行为不一致

`BottomNavBarWithFAB` 实际没有 FAB，只是普通底部导航。文档要求如果没有中心发布按钮，不得命名为 `BottomNavBarWithFAB`。

**证据**

- `frontend/android/app/src/main/java/com/antclaw/alfq/navigation/AlfQNavigation.kt:37-95`
- `docs/安卓客户端技术文档包/10-X-Threads社交客户端落地指导.md` 4.1

**建议**

- 要么实现真正中心发布 FAB。
- 要么重命名为 `BottomNavBar`，发布入口放在 Feed 顶部或信息流浮动按钮。

### 6.2 Web/Admin Token 存储策略偏弱

Web/Admin 将 token 放入 `localStorage`，多个模块直接读取。Android 使用 Jetpack Security，这是更合理方向。

**证据**

- `frontend/admin/src/lib/api.ts:68-70`
- `frontend/admin/src/lib/api.ts:117-129`
- `frontend/web/src/features/auth/api.ts:21-56`

**建议**

- 短期：封装 `authTokenStore`，禁止业务模块直接读写 localStorage。
- 中期：评估 httpOnly cookie 或内存 access token + refresh cookie。
- SSE query token 必须使用短生命周期 token 或服务端一次性订阅 token。

### 6.3 README 与实际结构不一致

README 仍提到 `frontend/mobile-rn`，但当前实际存在 `frontend/android`，且文档入口指向旧路径 `docs/开发环境与工具路径声明.md`，当前该文件在 `docs/旧文档/` 下。

**影响**

新 Agent 或开发者按 README 上手会走偏。

**建议**

- README 更新为当前结构：`web`、`admin`、`android`、`packages`。
- 明确首读文档：`AGENTS.md`、`docs/安卓客户端技术文档包/00-文档索引.md`、本报告。

## 七、建议整改路线

### 第一阶段：真实数据与错误契约收口

目标：禁止生产路径返回假数据。

- 移除 macro/calendar/user 的样例 fallback。
- 增加统一领域错误与 Connect code 映射。
- CI 增加 synthetic data 扫描。
- 更新 smoke：对无凭据/无数据场景断言明确错误，而不是 200 + 样例。

### 第二阶段：Android 会话与信息流体验收口

目标：让移动端高频路径稳定可用。

- `AlfQApp` 改由 `SessionViewModel` 驱动。
- Feed/Social 合并重复分页与乐观更新逻辑。
- 发布页补齐草稿、重试、成功回流 Feed。
- SSE 前后台、401、补拉未读建立端到端测试。

### 第三阶段：Admin/Web 工程化收口

目标：让管理端从原型页变成可维护工具。

- 拆分 `frontend/admin/src/lib/api.ts`。
- 替换 `setInterval` 为 SSE 或可控刷新 hook。
- 去除页面内 `alert/confirm` 和静默 catch。
- CI 强制 `pnpm -r build` / `pnpm -r lint`。

### 第四阶段：测试与文档一致性

目标：把 AGENTS.md 的规范变成自动化约束。

- 后端每个 service 包至少一个测试。
- Android 增加 ViewModel/Repository/SSE 测试。
- Web/Admin 增加 mapper/hook 测试。
- README 和文档索引清理旧结构、旧域名、旧说明。

## 八、建议新增自动化检查

| 检查 | 目标 | 建议实现 |
|---|---|---|
| 禁止合成数据 | 防止 fallback 污染生产 | `rg` 扫描 `sample data`、`demo@`、`generate.*Data`、`fallback data` |
| 禁止前端轮询 | 落实 SSE 优先 | 扫描 `setInterval(` |
| 禁止静默 catch | 防止无响应 UX | 扫描 `catch {}`、`catch { /* ignore */ }`、`catch (_: Exception) {}` |
| TS 强类型 | 降低 proto 漂移风险 | ESLint 禁 `any`，CI 不允许 `|| true` |
| Android 文案资源化 | 多语言一致性 | 扫描 Compose `Text("...")` 和 `contentDescription = "..."` |
| service 测试覆盖 | 落实 AGENTS 规范 | 脚本检查每个 `backend/internal/service/*` 至少一个 `_test.go` |

## 九、结语

这个项目当前最大风险不是技术栈选型，而是“规范、文档、实现、CI”四者没有闭环。建议停止继续堆功能，先完成一次质量收口：真实数据失败必须显性失败，客户端状态必须统一，会话/SSE 必须可测试，CI 必须真正拦截违规代码。完成这些后，后续 AI Agent 才能在稳定边界内继续扩展功能。
